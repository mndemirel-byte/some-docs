<Section id="s4" num="04" title="Things You Must Always Do">

<DoDontList>
  <DoItem title="1. Break every job into small pieces">
    <p>Instead of telling AI "rewrite this whole module," tell it to "complete this small vertical slice with these acceptance criteria."</p>
  </DoItem>
  <DoItem title="2. Watch token and context usage">
    <p>The model's performance drops over long sessions. Signs of declining quality: repeated mistakes, forgetting decisions it made earlier, producing irrelevant code. When you see these signs, clear the session and continue with fresh context. If the tool supports it, make token usage visible.</p>
  </DoItem>
  <DoItem title="3. Make the codebase readable for AI">
    <p>Well-named modules, clean interfaces, clear test boundaries, an up-to-date README, and local development commands directly increase agent success.</p>
  </DoItem>
  <DoItem title="4. Keep PRD and issue artifacts as files">
    <p>Decisions left in conversation with AI get lost. Decisions should be made permanent in the repository as Markdown issues, PRDs, ADRs, or test plans.</p>
  </DoItem>
  <DoItem title="5. Give AI the test commands explicitly">
    <CodeBlock lang="text — TypeScript/JS">
{`After implementation, run:
- npm test
- npm run typecheck
- npm run lint
- npm run build`}
    </CodeBlock>
    <CodeBlock lang="text — Python">
{`After implementation, run:
- pytest
- ruff check .
- mypy .`}
    </CodeBlock>
  </DoItem>
  <DoItem title="6. Never skip review">
    <p>As AI produces more code, the review burden grows. Human review and QA preserve quality and the engineering instinct we call "taste" — evaluating not just whether the code works, but whether it was designed correctly, is maintainable, and meets team standards.</p>
  </DoItem>
</DoDontList>

</Section>

<Section id="s5" num="05" title="Things You Must Never Do">

<DoDontList>
  <DontItem title='1. Don&apos;t try to build "an entire feature in one prompt"'>
    <p>It bloats context, grows scope, and makes the model harder to control.</p>
  </DontItem>
  <DontItem title="2. Don't just fix the spec and move on without reading the code">
    <p>This approach disconnects the developer from the code. <strong>Code is still the primary reality.</strong> Spec-first is correct in areas like API contracts and migration plans — but after writing the spec, you still need to read and understand the resulting code.</p>
  </DontItem>
  <DontItem title="3. Don't merge untested AI code">
    <p>Code AI produces may compile but might not behave correctly. It's not trustworthy without tests, typecheck, and a build.</p>
  </DontItem>
  <DontItem title="4. Don't blindly follow a horizontal phase plan">
    <p>A plan that goes database only → then API → then frontend delays feedback. Vertical slices should be preferred.</p>
  </DontItem>
  <DontItem title="5. Don't create huge CLAUDE.md / system prompt files">
    <p>Files like <code>CLAUDE.md</code> and <code>.cursorrules</code> should be kept small. If the starting context is too large, the model starts burning through its effective attention capacity before it even begins work.</p>
  </DontItem>
  <DontItem title="6. Don't leave stale documents lying around the repo">
    <p>Old PRDs or closed decision documents can mislead AI. PRDs should be closed and archived after implementation.</p>
  </DontItem>
</DoDontList>

</Section>

<Playbook
  icon={IconBuilding}
  iconColor="var(--accent-text)"

  steps={[
    <>A grilling session with <strong>domain expert + developer + AI.</strong></>,
    <>Produce a <strong>PRD.</strong></>,
    <>Build a <strong>prototype</strong> if a technical spike is needed.</>,
    <>Split the PRD into <strong>Kanban issues.</strong></>,

  ]}

<Section id="s9" num="09" title="An Example AI Coding Session Flow">

An example showing how all the stages turn into a real conversation in practice. Scenario: adding a simple points system to an education platform.

<Session>
  <DevTurn label="Developer">
    <p>Read this feature brief. Don&apos;t write code. Interrogate me first.</p>
  </DevTurn>
  <AiTurn label="AI">
    <ul>
      <li>Which user segment is this feature for?</li>
      <li>What's the success metric?</li>
      <li>Will existing data be processed retroactively?</li>
      <li>Where will the UI appear?</li>
      <li>What are the edge cases?</li>
    </ul>
  </AiTurn>
  <DevTurn label="Developer">
    <p>Gives the answers.</p>
  </DevTurn>
  <AiTurn label="AI">
    <p>Produces a PRD → <code>docs/prd/gamification-points.md</code></p>
  </AiTurn>
  <DevTurn label="Developer">
    <p>Split the PRD into vertical slice issues.</p>
  </DevTurn>
  <AiTurn label="AI">
    <ul>
      <li>Issue 01: Minimal end-to-end flow</li>
      <li>Issue 02: Edge case handling</li>
      <li>Issue 03: Admin visibility</li>
      <li>Issue 04: Migration / backfill</li>
      <li>Issue 05: Tests and cleanup</li>
    </ul>
  </AiTurn>
  <DevTurn label="Developer">
    <p>Implement Issue 01 using TDD. Don&apos;t go outside scope.</p>
  </DevTurn>
  <AiTurn label="AI">
    <p>Writes tests → implements → runs the tests → gives a summary.</p>
  </AiTurn>
  <DevTurn label="Developer">
    <p>Reviews, asks for changes, or merges.</p>
  </DevTurn>
</Session>

<Section id="s10" num="10" title="The Most Important Best Practices">

<NumberedGrid>
  <NumberedItem num={1}><strong>Don&apos;t have AI write code directly;</strong> ask it to interrogate you first.</NumberedItem>
  <NumberedItem num={2}>Aim for <strong>shared understanding, not a plan.</strong></NumberedItem>
  <NumberedItem num={3}><strong>Produce a PRD, but don&apos;t treat it as living truth;</strong> the code is the truth.</NumberedItem>
  <NumberedItem num={4}>Split issues as <strong>vertical slices.</strong></NumberedItem>
  <NumberedItem num={5}>Give the agent <strong>small, independent, testable</strong> work.</NumberedItem>
  <NumberedItem num={6}><strong>Use TDD;</strong> have AI write tests first.</NumberedItem>
  <NumberedItem num={7}><strong>Keep context small;</strong> don&apos;t rely on long sessions.</NumberedItem>
  <NumberedItem num={8}>When using sub-agents, <strong>keep the parent context clean.</strong></NumberedItem>
  <NumberedItem num={9}><strong>Build a deep module architecture;</strong> avoid the shallow dependency soup.</NumberedItem>
  <NumberedItem num={10}>Make <strong>human review and QA</strong> a mandatory part of the process.</NumberedItem>
  <NumberedItem num={11} wide><strong>AFK coding is not unconditionally safe;</strong> branch isolation, an iteration limit, and diff review are mandatory.</NumberedItem>
</NumberedGrid>

</Section>

<Section id="s11" num="11" title="Short Summary">

The essence of AI coding isn't "knowing how to write a prompt." The real issue is this:

<KeyQuote>
  Getting AI to do the right work, at the right size, with the right context, inside the right feedback loop.
</KeyQuote>

That's why a successful AI coding process can be reduced to this formula:

<Formula
  nodes={["Alignment", "PRD", "Vertical Slice Issues", "TDD Impl.", "Auto Checks", "Human Review", "Merge"]}
/>

AI coding doesn't automatically turn an undisciplined developer into a good one. On the contrary, **it amplifies the lack of discipline.** But combined with good software engineering practices, it becomes a powerful production model that ships well-planned, testable, small, independent pieces of work very quickly.

<Callout icon={IconSparkles} kind="tip">
  Taken together with Part 1, this framework forms the foundation for building an agentic software delivery workflow regardless of which language or tool you choose.
</Callout>

</Section>
