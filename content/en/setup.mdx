  <InfoCard icon={IconFileDescription} title="CLAUDE.md">

  </InfoCard>
  <InfoCard icon={IconTools} title=".claude/skills/">
    Reusable working disciplines. A skill is not a "role" — it is the <strong>procedure</strong> the agent applies.
  </InfoCard>
  <InfoCard icon={IconRobot} title=".claude/agents/">
    Specialist agent roles. Each agent owns a specific job and may use multiple skills.
  </InfoCard>
  <InfoCard icon={IconNotebook} title="docs/CONTEXT.md">
    The living context file. Domain language, key concepts, system boundaries, module responsibilities, and architectural assumptions.
  </InfoCard>
  <InfoCard icon={IconLayoutList} title="docs/prd/">
    Product requirements documents. E.g.: <code>001-initial-product-requirements.md</code>
  </InfoCard>
  <InfoCard icon={IconChecklist} title="docs/issues/">
    Work items handed to agents. Every issue must be a <strong>vertical slice</strong> — never a horizontal layer task.
  </InfoCard>
  <InfoCard icon={IconGitBranch} title="docs/adr/">
    Architecture Decision Records. E.g.: <code>0001-use-config-file-for-pricing.md</code>
  </InfoCard>
  <InfoCard icon={IconSitemap} title="docs/architecture/">
    System architecture, module map, data flow, sequence diagrams, and high-level design documents.
  </InfoCard>
  <InfoCard icon={IconNotes} title="docs/decisions/">
    Smaller product, technical, or process decisions that don't warrant a full ADR but still need tracking.
  </InfoCard>

<CodeBlock lang="markdown">
{`# Project Instructions for Claude Code

## Project Goal
This repository uses an agentic development workflow.
Claude should not work as a single monolithic coding assistant. Instead, Claude should:
1. Understand the project context.
2. Clarify requirements.
3. Produce PRDs when needed.
4. Break work into vertical slice issues.
5. Implement one issue at a time.
6. Use TDD for deterministic behavior.
7. Keep architecture decisions documented.
8. Review architecture before finalizing milestones.

## Repository Structure
Important folders:
- \`docs/CONTEXT.md\`: living project context and domain language
- \`docs/prd/\`: product requirements documents
- \`docs/issues/\`: agent-ready vertical slice implementation issues
- \`docs/adr/\`: architecture decision records
- \`docs/architecture/\`: high-level design and architecture notes
- \`docs/decisions/\`: smaller non-ADR decisions
- \`.claude/skills/\`: reusable workflows and engineering disciplines
- \`.claude/agents/\`: specialized project agents

## Default Workflow
For new features:
1. Use \`/grill-with-docs\` if the requirement is unclear.
2. Use \`/to-prd\` for medium or large features.
3. Use \`/to-issues\` to split PRD into vertical slice issues.
4. Use \`implementation-agent\` for implementation.
5. Implementation must follow \`/tdd\`.
6. Use \`/codebase-design\` when changing module boundaries.
7. Use \`debugging-agent\` with \`/diagnosing-bugs\` when tests fail unexpectedly.
8. Use \`/improve-codebase-architecture\` before milestone completion.

## Architecture Rules
- Prefer vertical slices over horizontal layer work.
- Keep business logic separate from presentation layers.
- Keep public interfaces small.
- Prefer deep modules over shallow modules.
- Avoid unnecessary abstraction.
- Avoid large rewrites unless explicitly requested.
- Do not duplicate business logic across UI, API, CLI, or worker layers.
- Document meaningful architecture decisions in \`docs/adr/\`.

## Testing Rules
- Use TDD for deterministic business logic.
- Write one failing test before implementation.
- Prefer behavior-focused tests.
- Do not couple tests to private implementation details unless necessary.
- Run relevant tests after each change.
- Run the full test suite before marking an issue complete.

## Documentation Rules
- Keep \`docs/CONTEXT.md\` updated when domain language or module boundaries change.
- Write PRDs under \`docs/prd/\`.
- Write implementation issues under \`docs/issues/\`.
- Write ADRs under \`docs/adr/\`.
- Keep README accurate for setup and usage.

## Issue Rules
Issues under \`docs/issues/\` must include:
- Title, User story, Acceptance criteria, Test expectations,
  Dependencies, Suggested agent, Required skills, Out of scope

Issues should be vertical slices. Avoid: "Create database layer", "Write pricing.py".
Prefer: "User can run the first CLI tracer bullet and see a cost estimate".

## Commands
\`\`\`bash
# Run tests
pytest

# Run app
# TODO: add project-specific run command
\`\`\`

## Safety and Scope
- Do not delete files without explicit instruction.
- Do not introduce new dependencies without explaining why.
- Do not change public behavior outside the active issue.
- Do not perform unrelated refactors.
- If a task is too broad, create or update an issue instead of coding immediately.`}
</CodeBlock>

</Disclosure>

<p><strong>Purpose:</strong> Drive implementation through the red-green-refactor loop.</p>
<p><strong>Steps:</strong></p>
<ol>
  <li>Read the issue acceptance criteria</li>
  <li>Pick a behavior</li>
  <li>Write a failing test</li>
  <li>Run the relevant test command</li>
  <li>Confirm the test fails for the expected reason</li>
  <li>Implement the smallest change that makes the test pass</li>
  <li>Run the test again</li>
  <li>Refactor once the test passes</li>
  <li>Repeat until all acceptance criteria are covered</li>
  <li>Run the full test suite before finishing</li>
</ol>
<p><strong>Test rules:</strong> Prefer behavior tests. Don't test private implementation details. Don't write brittle tests. Don't assert on volatile values. Use fixtures. Keep tests readable.</p>
<p><strong>Implementation rules:</strong> Don't write large amounts of production code before tests. Don't add unrelated features. Don't do unrelated refactors. Stay focused on the active issue.</p>

</Disclosure>

<Section id="s9" num="09" title="Recommended Workflow">

### When starting a new project

<WorkflowStep num={1} title="/grill-with-docs">
  Clarify the project, extract domain language, create <code>docs/CONTEXT.md</code>, list open questions
</WorkflowStep>
<WorkflowStep num={2} title="/to-prd">
  Write the first PRD under <code>docs/prd/</code>
</WorkflowStep>
<WorkflowStep num={3} title="/to-issues">
  Split the PRD into agent-ready vertical slice issues → <code>docs/issues/</code>
</WorkflowStep>

### When implementing an issue

<CodeBlock lang="text — Claude Code">
{`Use implementation-agent.

Implement docs/issues/001-example-feature.md.

Follow the tdd and codebase-design skills.
Keep changes scoped to this issue.
Run tests before finishing.`}
</CodeBlock>

### When a test breaks

<CodeBlock lang="text — Claude Code">
{`Use debugging-agent.

Diagnose the failing test using the diagnosing-bugs skill.
Do not rewrite large sections.
Add a regression test if appropriate.`}
</CodeBlock>

### At the end of a milestone

<CodeBlock lang="text — Claude Code">
{`Use architecture-review-agent.

Run improve-codebase-architecture.
Review module boundaries, tests, docs and ADRs.
Apply only low-risk fixes.`}
</CodeBlock>

</Section>

  </InfoCard>
  <InfoCard icon={IconRobot} title="What is an agent?" variant="inline">
