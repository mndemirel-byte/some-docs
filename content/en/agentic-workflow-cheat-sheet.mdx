<Section id="mental" num="01" title="Mental model">

<CardGrid>
  <InfoCard icon={IconAdjustments} title="rules">

  </InfoCard>
  <InfoCard icon={IconFileDescription} title="CLAUDE.md">
    Repository-level project memory: goal, critical commands, architecture notes, and test instructions. Use for project-specific facts Claude should frequently remember.
  </InfoCard>
  <InfoCard icon={IconSettings} title="settings.json">
    Permissions, hook definitions, env/config, tool behavior, and shared project settings. Use when you need real configuration, not prose instructions.
  </InfoCard>
  <InfoCard icon={IconTerminal2} title="commands">
    Claude Code's own built-in slash commands. New custom command workflows are now effectively managed through <code>skills</code> instead.
  </InfoCard>
  <InfoCard icon={IconTools} title="skills">
    Reusable procedures and slash-command entrypoints, which can dispatch an agent when needed. Use when a workflow should be reused or exposed as <code>/plan</code>, <code>/work</code>, <code>/review</code>.
  </InfoCard>
  <InfoCard icon={IconRobot} title="agents">
    Specialized execution contexts: role, model, tools, permissions, and behavioral boundaries. Use when planning, implementation, and review need different tools or permissions.
  </InfoCard>
  <InfoCard icon={IconGitBranch} title="hooks">
    Tool lifecycle automation: before/after tool use, after edit, on stop, etc. Use for deterministic checks, safety, formatting, or test reminders.
  </InfoCard>
</CardGrid>

<Callout kind="tip">
  <strong>Quick distinction:</strong> <code>rules</code> define behavior standards, <code>CLAUDE.md</code> is the project manifest, <code>skills</code> are procedures, <code>agents</code> are roles, <code>hooks</code> are automation.
</Callout>

<Callout kind="info">
  <strong>Skill ↔ Agent relationship:</strong> In practical setups, a skill is usually the workflow entrypoint — <code>/plan</code>, <code>/work</code>, <code>/review</code>. The skill may dispatch agents or ask agents for focused work. An agent defines the role, tool set, model, and boundaries. Official docs also support running a skill directly in a forked subagent via <code>context: fork</code> + <code>agent:</code>, but that's an advanced pattern, not required for the main workflow.
</Callout>

<Section id="rules" num="05" title="rules">

<code>.claude/rules/</code> lets you split persistent instructions into modular files instead of growing one huge <code>CLAUDE.md</code>. Rules are behavior/project instructions Claude should know. The important nuance: <strong>rules without path scoping load at session start</strong>; rules with <code>paths</code> frontmatter load when Claude works with matching files. If you do not split and scope rules, they can bloat the session context.

<CodeBlock lang="text" kind="file">
{`.claude/
└─ rules/
   ├─ always.md              # tiny global rules; loads every session
   ├─ testing.md             # general test rules; loads every session if no paths
   ├─ frontend/
   │  └─ react.md            # path-scoped to React/TSX files
   └─ backend/
      └─ api.md              # path-scoped to API files`}
</CodeBlock>

<Callout kind="info">
  <strong>Why frontmatter matters:</strong> Rule files are markdown files with optional YAML frontmatter. The most useful field is <code>paths</code>. Without <code>paths</code>, the rule is global and may load at session start. With <code>paths</code>, Claude loads the rule when working with matching files. The goal is to avoid reading every rule up front and instead load the rule Claude needs for the current files.
</Callout>

<CodeBlock lang="markdown" kind="file">
{`---
paths:
  - "src/api/**/*.ts"
  - "app/api/**/*.ts"
  - "server/**/*.ts"
---

# API Rules

- Validate request input at the boundary.
- Return the shared error response shape.
- Keep database access behind the repository/service layer.
- Add or update tests for behavior changes.`}
</CodeBlock>

<CodeBlock lang="markdown" kind="file">
{`---
paths:
  - "src/**/*.tsx"
  - "app/**/*.tsx"
  - "components/**/*.tsx"
---

# React / UI Rules

- Prefer small, focused components.
- Keep server/client boundaries explicit.
- Do not introduce a new UI library without approval.
- Add accessible labels for interactive elements.`}
</CodeBlock>

<DataTable
  headers={["Rule type", "How it loads", "What to put there"]}
  rows={[
    ["Global rule (.claude/rules/always.md)", "Without paths, it can load at session start.", "Tiny always-needed rules: safety, general review standard, commit discipline."],
    ["Path-scoped rule (paths: frontmatter)", "Loads when Claude reads or works on matching files.", "API, frontend, test, database, mobile, or other area-specific rules."],
    ["Skill", "Loads when invoked by the user or when Claude decides it is relevant.", "Multi-step procedures: plan, implement, review, diagnose, prepare commit."],
    ["Hook / settings", "Runs as config/lifecycle behavior, not as something the model remembers.", "Permissions, command checks, automatic reminders, or policy enforcement."],
  ]}
/>

<Callout kind="tip">
  <strong>Practical rule strategy:</strong> Keep <code>CLAUDE.md</code> and global rules minimal. If the answer to "must Claude know this in every task?" is no, make the rule path-scoped or move it into a skill. Do not put large checklists into global rules. Split them by area: API rules for <code>{"src/api/**"}</code>, UI rules for <code>{"**/*.tsx"}</code>, test rules for <code>{"**/*.test.ts"}</code>.
</Callout>

</Section>

    "allow": [
      "Bash(npm test)",

      "Bash(npm run typecheck)",

    ],
    "deny": [
      "Bash(rm -rf /)",
      "Bash(git push --force*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'File changed. Consider running tests.'"
          }
        ]
      }
    ]
  }
}`}
</CodeBlock>

<Callout kind="tip">
  <strong>Best practice:</strong> Shared team settings belong in project scope at <code>.claude/settings.json</code>; personal permissions and local paths/env values belong in <code>.claude/settings.local.json</code>. Keep <code>settings.local.json</code> out of git; Claude adds it to gitignore when it creates the file, but add it yourself if you create it manually.
</Callout>

</Section>

<Section id="commands" num="07" title="commands">

In Claude Code, <strong>commands</strong> means two different things: Claude Code's built-in slash commands and older custom command workflows that used to live under <code>.claude/commands/</code>. In a modern setup, custom reusable workflows should generally be implemented as <code>skills</code>.

<Callout kind="tip">
  <strong>Current distinction:</strong> Built-in commands such as <code>/usage</code>, <code>/context</code>, <code>/compact</code>, <code>/clear</code>, and <code>/model</code> are still separate. But for new custom workflows, prefer <code>.claude/skills/&lt;name&gt;/SKILL.md</code>. Treat <code>.claude/commands/</code> as legacy/backward-compatible.
</Callout>

<Callout kind="info">
  <strong>Name collision note:</strong> For readability, this document shows skill-backed command examples as <code>/plan</code>, <code>/work</code>, and <code>/review</code>. If those names collide with built-in commands in your Claude Code version, use a plugin namespace such as <code>/agentic:plan</code> or choose a team-specific name.
</Callout>

<Section id="skills" num="08" title="skills">

A skill is a reusable procedure and can act as a slash-command entrypoint. The recommended place for modern custom workflows is <code>.claude/skills/&lt;name&gt;/SKILL.md</code>. In this reference, skills are the main user-facing workflow surface: <code>/plan</code>, <code>/work</code>, <code>/review</code>.

<Callout kind="info">
  <strong>Discovery/path note:</strong> For project/personal skills, the expected layout is <code>.claude/skills/plan/SKILL.md</code>; a flat file like <code>.claude/skills/plan.md</code> is not loaded as a skill. The command you type comes from the directory name: <code>.claude/skills/plan/SKILL.md</code> → <code>/plan</code>. The frontmatter <code>name</code> field can change the display label shown in the slash menu, but in most skill locations it does not change the command you type. Exception: plugin root <code>SKILL.md</code>.
</Callout>

<Callout kind="info">
  <strong>Small discovery notes:</strong> If <code>.claude/commands/plan.md</code> and <code>.claude/skills/plan/SKILL.md</code> both exist, the skill takes precedence. Claude live-detects changes inside skill directories that existed when the session started; if <code>.claude/skills/</code> did not exist at startup, restart Claude so it can watch the new directory. In monorepos, nested <code>.claude/skills/</code> folders can become available when Claude works in those subdirectories.
</Callout>

<Callout kind="info">
  <strong>Skill ↔ agent invocation model:</strong> Skills can request help from agents when useful; for example, the <code>/review</code> skill can delegate a non-trivial diff to the <code>reviewer</code> agent. Agents can also discover and invoke relevant skills during execution if they have access to the <code>Skill</code> tool. Best practice: keep the user-facing workflow in the skill, and keep role, tool, model, and permission boundaries in the agent.
</Callout>

    ["Hook/settings", "Enforcement, permissions, and lifecycle automation that must work even if the model forgets.", "Fully automating creative judgment, product reasoning, or steps that need human approval."],

/>

<Callout kind="tip">
  <strong>Recommended model for this setup:</strong> Make <code>/plan</code>, <code>/work</code>, and <code>/review</code> skill-backed commands. Agents are specialized workers those skills can call when useful. This lets participants start by copying skills and add agents as the workflow matures.
</Callout>

<Callout kind="info">
  <strong>Invocation control:</strong> Skills can be invoked in two ways: the user can call them directly with <code>/skill-name</code>, or Claude can invoke them automatically when their description matches the task. The default allows both. Use <code>disable-model-invocation: true</code> for manual-only workflows. Use <code>user-invocable: false</code> for background knowledge that should not appear as a user-facing slash command.
</Callout>

# Plan Skill

Use this skill when the request is unclear, broad, risky, or larger than one small implementation step.

<Section id="agents" num="09" title="agents">

An agent is an execution context for a role: system prompt, model, tool set, permission mode, and output expectations live here. In this setup, agents can be invoked directly, but the more practical model is for skills such as <code>/plan</code>, <code>/work</code>, and <code>/review</code> to request help from the relevant agents when useful.

<Callout kind="info">
  <strong>Important:</strong> The <code>skills:</code> field preloads selected skill content into the agent at startup. In plain terms, the agent receives that skill's full text before it starts working. This is useful for conventions/reference knowledge the agent must always know, but preloading everything bloats context. Skills with <code>disable-model-invocation: true</code> cannot be preloaded. Even without preload, an agent can still discover and invoke relevant project/user/plugin skills during execution if it has access to the Skill tool.
</Callout>

<CodeBlock lang="markdown" kind="example">
{`---
name: api-worker
description: Implements API changes using team conventions.
tools: Read, Write, Edit, Bash, Glob, Grep, Skill
model: sonnet
skills:
  - api-conventions
  - error-handling-patterns
---

You implement one scoped API task. Follow the preloaded conventions.`}
</CodeBlock>

<Section id="hooks" num="10" title="hooks">

A hook is a command/script that runs automatically at specific Claude Code lifecycle points. Hooks are good for small deterministic checks that should not depend on the LLM remembering them.

<DataTable
  headers={["Hook type", "Example use"]}
  rows={[
    ["PreToolUse", "Block risky bash commands or require approval."],
    ["PostToolUse", "Remind/run tests or formatting after edits."],
    ["Stop", "Produce an end-of-session summary/checklist."],
    ["Notification", "Notify when user attention/approval is needed."],
  ]}
/>

<CodeBlock lang="python" kind="file">
{`#!/usr/bin/env python3
import json
import sys

payload = json.load(sys.stdin)
tool_name = payload.get("tool_name", "")

if tool_name in {"Write", "Edit", "MultiEdit"}:
    print("Reminder: file changed. Run the smallest relevant test before continuing.")

sys.exit(0)`}
</CodeBlock>

<CodeBlock lang="json" kind="file">
{`{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(npm run lint)",
      "Bash(npm run typecheck)",
      "Bash(npm run build)"
    ],
    "deny": [
      "Bash(rm -rf /)",
      "Bash(git push --force*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'File changed. Consider running tests.'"
          }
        ]
      }
    ]
  }
}`}
</CodeBlock>

<Callout kind="tip">
  <strong>Hook best practice:</strong> Keep hooks boring and safe. Big business logic, complex decisions, or noisy checks are poor hook candidates.
</Callout>

</Section>

<Section id="context" num="12" title="context / token management">

<FlowSteps>
  <FlowStep num={1} title="Keep sessions small.">
    One session = one phase or one small issue. Split Plan, Work, and Review when they get long.
  </FlowStep>
  <FlowStep num={2} title="Write decisions to files.">
    Important decisions are lost if they only live in chat. Put them in issues, ADRs, README, or context docs.
  </FlowStep>
  <FlowStep num={3} title="Use compact/clear when context grows.">
    First write active scope, decisions, test results, and next step into files.
  </FlowStep>
  <FlowStep num={4} title="Choose models by task type.">
    Planning and review require more reasoning; simple edits may use cheaper models.
  </FlowStep>
</FlowSteps>
