{`# Project Instructions for Claude Code

## Project Goal
This repository uses an agentic development workflow.
Claude should not work as a single monolithic coding assistant. Instead, Claude should:
1. Understand the project context.
2. Clarify requirements.
3. Produce PRDs when needed.
4. Break work into vertical slice issues.
5. Implement one issue at a time.
6. Use TDD for deterministic behavior.
7. Keep architecture decisions documented.
8. Review architecture before finalizing milestones.

## Repository Structure
Important folders:
- \`docs/CONTEXT.md\`: living project context and domain language
- \`docs/prd/\`: product requirements documents
- \`docs/issues/\`: agent-ready vertical slice implementation issues
- \`docs/adr/\`: architecture decision records
- \`docs/architecture/\`: high-level design and architecture notes
- \`docs/decisions/\`: smaller non-ADR decisions
- \`.claude/skills/\`: reusable workflows and engineering disciplines
- \`.claude/agents/\`: specialized project agents

## Default Workflow
For new features:
1. Use \`/grill-with-docs\` if the requirement is unclear.
2. Use \`/to-prd\` for medium or large features.
3. Use \`/to-issues\` to split PRD into vertical slice issues.
4. Use \`implementation-agent\` for implementation.
5. Implementation must follow \`/tdd\`.
6. Use \`/codebase-design\` when changing module boundaries.
7. Use \`debugging-agent\` with \`/diagnosing-bugs\` when tests fail unexpectedly.
8. Use \`/improve-codebase-architecture\` before milestone completion.

## Architecture Rules
- Prefer vertical slices over horizontal layer work.
- Keep business logic separate from presentation layers.
- Keep public interfaces small.
- Prefer deep modules over shallow modules.
- Avoid unnecessary abstraction.
- Avoid large rewrites unless explicitly requested.
- Do not duplicate business logic across UI, API, CLI, or worker layers.
- Document meaningful architecture decisions in \`docs/adr/\`.

## Testing Rules
- Use TDD for deterministic business logic.
- Write one failing test before implementation.
- Prefer behavior-focused tests.
- Do not couple tests to private implementation details unless necessary.
- Run relevant tests after each change.
- Run the full test suite before marking an issue complete.

## Documentation Rules
- Keep \`docs/CONTEXT.md\` updated when domain language or module boundaries change.
- Write PRDs under \`docs/prd/\`.
- Write implementation issues under \`docs/issues/\`.
- Write ADRs under \`docs/adr/\`.
- Keep README accurate for setup and usage.

## Issue Rules
Issues under \`docs/issues/\` must include:
- Title, User story, Acceptance criteria, Test expectations,
  Dependencies, Suggested agent, Required skills, Out of scope

Issues should be vertical slices. Avoid: "Create database layer", "Write pricing.py".
Prefer: "User can run the first CLI tracer bullet and see a cost estimate".

## Commands
\`\`\`bash
# Run tests
pytest

# Run app
# TODO: add project-specific run command
\`\`\`

## Safety and Scope
- Do not delete files without explicit instruction.
- Do not introduce new dependencies without explaining why.
- Do not change public behavior outside the active issue.
- Do not perform unrelated refactors.
- If a task is too broad, create or update an issue instead of coding immediately.`}
</CodeBlock>
