{`---
name: code-reviewer
description: Reviews completed code changes for correctness, regressions, security risks, and missing tests. Use after implementation or before creating a PR.
tools: Read, Grep, Glob, Bash
model: sonnet
color: purple
---

You review the current change set only.

Focus on:
- correctness and regressions
- security and data-loss risks
- missing or weak tests
- violations of existing project conventions

Do not edit files.
Use Bash only to inspect diffs or run targeted checks.
Stop after you have enough evidence to produce the report.

Return:
1. Verdict: PASS or NEEDS_CHANGES
2. Findings ordered by severity
3. Evidence with file paths and line references
4. Recommended fixes
5. Checks performed and any obstacles`}
</CodeBlock>

<Section id="description" num="05" title="Descriptions">

Description iki işi aynı anda yapar: Claude'un <strong>ne zaman</strong> delegate edeceğini söyler ve parent'ın subagent'a yazacağı task prompt'un yönünü etkiler.

<DoDontList>
  <DontItem title="Bad">
    <CodeBlock lang="yaml">
{`description: Expert reviewer for code.`}
    </CodeBlock>
    Belirsiz tetikleyici, belirsiz scope, belirsiz sonuç.
  </DontItem>
  <DoItem title="Good">
    <CodeBlock lang="yaml">
{`description: Reviews completed code changes for correctness, regressions, security risks, and missing tests. Use after implementation or before creating a PR.`}
    </CodeBlock>
    Ne yaptığı, ne zaman kullanılacağı ve neye bakacağı açık.
  </DoItem>
</DoDontList>

<Callout>
  <strong>Formula:</strong> <code>[What it does] + [What it inspects] + [When to use it]</code>
</Callout>

<p>
Persona yerine davranış yaz. "Expert Flutter dev" gibi bir ifade; <strong>scope</strong> söylemez, <strong>ne zaman</strong> çağrılacağını söylemez ve parent'ın iyi task prompt yazmasına yardım etmez. Daha iyi yaklaşım: alanı ve işi açıkla — örn. <code>Reviews Flutter UI changes for state bugs, layout regressions, accessibility issues, and missing widget tests. Use before opening a PR.</code>
</p>

</Section>

<Section id="output" num="07" title="Structured Output">

Yapılandırılmış çıktı yalnızca okunabilirlik sağlamaz. Agent'ın "işim ne zaman bitti?" sorusuna doğal bir cevap verir ve gereksiz araştırmayı durdurur.

<CodeBlock lang="markdown" kind="file">
{`## Verdict
PASS | NEEDS_CHANGES | BLOCKED

## Findings
- [severity] finding
  - Evidence: file:line or command output
  - Impact: why it matters
  - Recommendation: specific next step

## Checks Performed
- ...

## Obstacles / Unknowns
- What could not be verified
- Why

## Summary
Maximum 5 bullets.`}
</CodeBlock>

<Section id="anti" num="11" title="Anti-patterns">

<DoDontList>
  <DontItem title="Expert Personas">
    <p>"Senior architect agent" adı tek başına kalite getirmez. Scope, tool ve output kontratı yoksa sadece süslü bir rol olur.</p>
    <p>Neden? Çünkü kıdem etiketi task tasarımı yerine kişilik vurgular. Claude'un ihtiyaç duyduğu şey "kim olduğu" değil, "ne yapacağı ve neye bakacağı"dır.</p>
  </DontItem>
  <DontItem title="Test Runner Agents">
    Sadece deterministik bir komut çalıştırmak için agent kullanmak gereksiz maliyet ve context yaratır. Hook veya doğrudan Bash daha uygundur.
  </DontItem>
</DoDontList>

<Section id="tldr" num="14" title="TL;DR">

<CardGrid columns="two">
  <InfoCard icon={IconVolumeOff} title="Isolate noise.">
    Search, logs ve geçici dosya içeriğini main thread'den uzak tut.
  </InfoCard>
  <InfoCard icon={IconClipboardList} title="Keep decisions.">
    Gereksinimler, trade-off'lar ve kullanıcı kararları ana thread'de kalsın.
  </InfoCard>
  <InfoCard icon={IconLock} title="Constrain tools.">
    Her agent'a yalnızca görevi için gereken araçları ver.
  </InfoCard>
  <InfoCard icon={IconFlagCheck} title={'Define "done."'}>
    Structured output ve stop condition ile işi sonlu hale getir.
  </InfoCard>
</CardGrid>

<Callout kind="tip">
  <strong>Final rule:</strong> Ara iş önemliyse main thread. Ara iş gürültüyse subagent.
</Callout>

</Section>
