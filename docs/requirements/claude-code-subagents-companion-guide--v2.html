01

Mental Model

Subagent, ana konuşmadan ayrı bir context window içinde belirli bir işi yapan ve sonuç olarak yalnızca özet döndüren uzman worker’dır.

A subagent is a specialized worker that performs a specific task in a separate context window and returns only a summary.

🧠 Main thread keeps decisions🧪 Subagent absorbs noisy work📦 Only the result comes back
Ana fikir:Key takeaway: Subagent daha akıllı bir agent değildir. İzole bir execution environment’tır.A subagent is not a smarter agent. It is an isolated execution environment.

Main Thread vs Subagent

DimensionMain ThreadSubagent
ContextKullanıcı konuşması, kararlar ve devam eden iş.Ayrı context; görev prompt’u ve kendi sistem talimatı.User conversation, decisions, and ongoing work.Separate context with task prompt and custom system instructions.
VisibilityAra adımlar görünür ve konuşmada kalır.Ara çalışma izole kalır; özet geri döner.Intermediate work stays visible in the conversation.Intermediate work stays isolated; a summary returns.
Tool callsAna akışın izinleriyle çalışır.Özel allowlist / denylist ile sınırlandırılabilir.Uses the main session’s permissions.Can be constrained with a dedicated allowlist or denylist.
Context growthSearch sonuçları ve log’lar ana context’i şişirir.Gürültülü veri kendi context’inde kalır.Search results and logs grow the main context.Noisy data stays inside its own context.
ReturnTüm konuşma devam eder.Kısa sonuç, bulgular veya öneri döner.The whole conversation continues.Returns a concise result, findings, or recommendation.

YES — Main Thread

Ara çalışma ileride alınacak kararları etkiliyorsa, kullanıcıyla tartışılacaksa veya debug sırasında adım adım görünürlük gerekiyorsa.

Use it when intermediate work affects later decisions, needs user discussion, or must stay visible during debugging.

↔

NO — Subagent

Ara çalışma yalnızca sonuca ulaşmak için gerekiyorsa ve sonrasında tekrar kullanılmayacaksa.

Use it when intermediate work is only needed to reach the result and will not be referenced again.

Decision Rule: Does the intermediate work matter? YES → Main Thread · NO → Subagent
03

Subagent Lifecycle

01

User

Bir hedef veya problem verir.

Provides a goal or problem.

02

Main Agent

Görevin izole edilip edilmeyeceğine karar verir.

Decides whether the work should be isolated.

03

Task Prompt

Amaç, scope, beklenen çıktı ve gerekli context yazılır.

Defines goal, scope, expected output, and required context.

04

Launch Subagent

Özel system prompt, model ve tool sınırları devreye girer.

Custom system prompt, model, and tool boundaries become active.

05

Research / Work

Dosyalar, aramalar, testler veya analiz kendi context’inde yürür.

Files, searches, tests, or analysis run inside its own context.

06

Summary

Yapılandırılmış ve kısa sonuç ana thread’e döner.

A concise, structured result returns to the main thread.

07

Destroy Context

Ara çalışma ana context’e taşınmaz; yalnızca sonuç kalır.

Intermediate work is not copied into the main context; only the result remains.

04

Anatomy of a Subagent

YAML Frontmatter

Kimlik, delegation açıklaması, tools, model ve UI rengi.

Identity, delegation description, tools, model, and UI color.

System Prompt

Rol değil; scope, davranış, sınır ve çıktı kontratı.

Not just a role; it defines scope, behavior, boundaries, and output contract.

.claude/agents/code-reviewer.md
---
name: code-reviewer
description: Reviews completed code changes for correctness, regressions, security risks, and missing tests. Use after implementation or before creating a PR.
tools: Read, Grep, Glob, Bash
model: sonnet
color: purple
---

You review the current change set only.

Focus on:
- correctness and regressions
- security and data-loss risks
- missing or weak tests
- violations of existing project conventions

Do not edit files.
Use Bash only to inspect diffs or run targeted checks.
Stop after you have enough evidence to produce the report.

Return:
1. Verdict: PASS or NEEDS_CHANGES
2. Findings ordered by severity
3. Evidence with file paths and line references
4. Recommended fixes
5. Checks performed and any obstacles
Güncel not:Current note: Yalnızca name ve description zorunludur. model verilmezse inherit; tools verilmezse mevcut araçlar miras alınır.Only name and description are required. Omitting model defaults to inherit; omitting tools inherits available tools.
05

Writing Great Descriptions

Description iki işi aynı anda yapar: Claude’un ne zaman delegate edeceğini söyler ve parent’ın subagent’a yazacağı task prompt’un yönünü etkiler.

The description has two jobs: it tells Claude when to delegate and influences how the parent frames the task prompt.

✕ Bad

description: Expert reviewer for code.

Belirsiz tetikleyici, belirsiz scope, belirsiz sonuç.

Vague trigger, vague scope, vague outcome.

✓ Good

description: Reviews completed code changes for correctness, regressions, security risks, and missing tests. Use after implementation or before creating a PR.

Ne yaptığı, ne zaman kullanılacağı ve neye bakacağı açık.

Clear job, trigger, and focus areas.

Formula: [What it does] + [What it inspects] + [When to use it]
Persona yerine davranış yaz. “Expert Flutter dev” gibi bir ifade; scope söylemez, ne zaman çağrılacağını söylemez ve parent’ın iyi task prompt yazmasına yardım etmez. Daha iyi yaklaşım: alanı ve işi açıkla — örn. Reviews Flutter UI changes for state bugs, layout regressions, accessibility issues, and missing widget tests. Use before opening a PR.Prefer behavior over persona. A label like “expert Flutter dev” does not define scope, does not tell Claude when to invoke the agent, and does not help the parent write a good task prompt. A better pattern is to name the domain and the job explicitly — for example: Reviews Flutter UI changes for state bugs, layout regressions, accessibility issues, and missing widget tests. Use before opening a PR.

System Prompt Design

01Scope
Tam olarak neyi kapsıyor?What exactly is in scope?
02Focus
Hangi sinyalleri önceliklendirmeli?Which signals matter most?
03Stop condition
Ne zaman yeterli kanıt var?When is there enough evidence?
04Structured output
Sonuç hangi şablonda dönmeli?What shape should the result take?
05Obstacle reporting
Neyi doğrulayamadı ve neden?What could not be verified, and why?
06Boundaries
Neyi yapmamalı?What must it not do?
Kaçın:Avoid: “Sen dünya çapında kıdemli bir uzmansın” gibi persona ağırlıklı prompt’lar yerine görev sınırı ve çıktı kontratı yaz.Replace persona-heavy prompts like “You are a world-class senior expert” with task boundaries and an output contract.
07

Structured Output

Yapılandırılmış çıktı yalnızca okunabilirlik sağlamaz. Agent’ın “işim ne zaman bitti?” sorusuna doğal bir cevap verir ve gereksiz araştırmayı durdurur.

Structured output is not only about readability. It gives the agent a natural answer to “when am I done?” and prevents endless exploration.

result contract
## Verdict
PASS | NEEDS_CHANGES | BLOCKED

## Findings
- [severity] finding
  - Evidence: file:line or command output
  - Impact: why it matters
  - Recommendation: specific next step

## Checks Performed
- ...

## Obstacles / Unknowns
- What could not be verified
- Why

## Summary
Maximum 5 bullets.

Readable

Parent sonuçları hızlı işler.

The parent can process results quickly.

Comparable

Farklı run’lar aynı formatta karşılaştırılır.

Different runs can be compared consistently.

Finite

Şablon tamamlandığında iş biter.

The task ends when the contract is filled.

Tool Permissions

Least Privilege: Agent’a “belki gerekir” diye araç verme. Görevi tamamlamak için gereken minimum araç setini ver.Do not grant tools “just in case.” Grant the minimum set required to complete the task.
AgentRecommended toolsWhy
Research AgentRead, Grep, GlobKod tabanını keşfeder; değişiklik yapmaz.Explores the codebase without changing it.
ReviewerRead, Grep, Glob, BashDiff ve test çıktısı görür; dosya edit’lemez.Inspects diffs and targeted checks without editing files.
WriterRead, Write, EditDoküman üretir veya günceller.Creates or updates documentation.
Styling AgentRead, Grep, Glob, EditUI dosyalarını bulur ve kontrollü değişiklik yapar.Finds UI files and makes scoped changes.
Reviewer neden Bash ister ama Edit istemez?Why does a reviewer need Bash but not Edit? Çünkü güvenilir review için git diff, test veya lint çalıştırması gerekebilir; fakat review ile implementasyonun birbirine karışmaması için dosya değiştirmemelidir.Reliable review may require git diff, tests, or linting, but it should not modify files because review and implementation must remain separate.
09

Choosing Models

⚡

Haiku

Hızlı arama, sınıflandırma, küçük ve net görevler.

Fast lookup, classification, and small well-defined tasks.

⚖️

Sonnet

Çoğu research, review ve pratik coding görevi için dengeli varsayılan.

Balanced default for most research, review, and practical coding tasks.

🧠

Opus

Yüksek belirsizlik, derin reasoning veya pahalı hataların olduğu işler.

High ambiguity, deep reasoning, or tasks where mistakes are costly.

↩️

Inherit

Parent ile aynı modeli kullanır; emin değilsen iyi başlangıç.

Uses the parent model; a sensible starting point when unsure.

Basit kural:Simple rule: Görev ne kadar rutin ve doğrulanabilir ise o kadar küçük model; belirsizlik ve karar maliyeti arttıkça daha güçlü model.The more routine and verifiable the task, the smaller the model can be. Increase capability as ambiguity and decision cost rise.

11

Anti-patterns

Expert Personas

“Senior architect agent” adı tek başına kalite getirmez. Scope, tool ve output kontratı yoksa sadece süslü bir rol olur.

A “senior architect agent” label does not create quality. Without scope, tools, and an output contract, it is only a fancy persona.

Neden? Çünkü kıdem etiketi task tasarımı yerine kişilik vurgular. Claude’un ihtiyaç duyduğu şey “kim olduğu” değil, “ne yapacağı ve neye bakacağı”dır.

Why? Because a seniority label emphasizes persona instead of task design. Claude needs to know not who it “is,” but what it should do and inspect.

Test Runner Agents

Sadece deterministik bir komut çalıştırmak için agent kullanmak gereksiz maliyet ve context yaratır. Hook veya doğrudan Bash daha uygundur.

Using an agent only to run a deterministic command adds unnecessary cost and context. Prefer a hook or direct Bash.

Sequential Pipelines

Her handoff, bilgiyi sıkıştırır ve nüans kaybı yaratır. Bir pipeline gerekiyorsa kritik kararları yaşayan bir dosyada tut veya ana thread’in orchestration yapmasını sağla.

Every handoff compresses information and loses nuance. When a pipeline is necessary, keep critical decisions in a living file or let the main thread orchestrate the work.

Should I Use a Subagent?

1. Do I need the intermediate work later?
YES → Main Thread
NO → Continue
2. Will the task produce lots of logs, search results, or file content?
YES → Subagent
NO → Continue
3. Do I need a fresh perspective separated from implementation context?
YES → Subagent
NO → Continue
4. Do I need step-by-step debugging visibility?
YES → Main Thread
NO → Continue
5. Is the task only a deterministic command?
YES → Bash / Hook
NO → Subagent may help

TL;DR

Isolate noise.

Search, logs ve geçici dosya içeriğini main thread’den uzak tut.

Keep search results, logs, and temporary file content out of the main thread.

Keep decisions.

Gereksinimler, trade-off’lar ve kullanıcı kararları ana thread’de kalsın.

Keep requirements, trade-offs, and user decisions in the main thread.

Constrain tools.

Her agent’a yalnızca görevi için gereken araçları ver.

Give each agent only the tools required for its task.

Define “done.”

Structured output ve stop condition ile işi sonlu hale getir.

Use structured output and a stop condition to make the task finite.

Final rule: Ara iş önemliyse main thread. Ara iş gürültüyse subagent.If intermediate work matters, use the main thread. If it is noise, use a subagent.
