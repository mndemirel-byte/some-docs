Quick distinction: rules define behavior standards, CLAUDE.md is the project manifest, skills are procedures, agents are roles, hooks are automation.
Skill ↔ Agent ilişkisi: Pratik kullanımda skill genellikle workflow entrypoint'idir: /plan, /work, /review gibi. Skill'in içinde agent dispatch edilebilir veya agent'lardan destek istenebilir. Agent ise rol, araç seti, model ve sınırları tanımlayan execution context'tir. Resmi dokümanda context: fork + agent: ile skill'i doğrudan forked subagent içinde çalıştırma desteği de var; ancak bu ileri seviye pattern'dir, ana akışta şart değildir.
Skill ↔ Agent relationship: In practical setups, a skill is usually the workflow entrypoint: /plan, /work, /review. The skill may dispatch agents or ask agents for focused work. An agent defines the role, tool set, model, and boundaries. Official docs also support running a skill directly in a forked subagent via context: fork + agent:, but that is an advanced pattern, not required for the main workflow.

04

CLAUDE.md

CLAUDE.md, repo seviyesinde Claude'un projeyi anlamasına yardım eden ana manifesttir. Çok uzun prosedürleri buraya gömmek yerine skill dosyalarına taşımak daha sürdürülebilirdir.

CLAUDE.md is the repository-level manifest that helps Claude understand the project. Long procedures should usually live in skills instead.

İyi içerikler

  • Proje amacı
  • Setup/test/build komutları
  • Mimari sınırlar
  • Güvenlik ve scope kuralları
  • Önemli dosya/klasör açıklamaları

Kaçınılacak şeyler

  • Çok uzun prompt metinleri
  • Her feature'ın geçici detayı
  • Güncel tutulmayacak roadmap'ler
  • Plugin/skill ile paylaşılması gereken prosedürler

Good content

  • Project goal
  • Setup/test/build commands
  • Architecture boundaries
  • Safety and scope rules
  • Important file/folder notes

Avoid

  • Very long prompt bodies
  • Temporary feature details
  • Roadmaps that will not be maintained
  • Procedures that should live in a plugin/skill
CLAUDE.md · template
# Project Instructions

## Project Context
- Project type: TODO
- Primary language/framework: TODO
- Main entry points: TODO
- Important commands: TODO

## Workflow
Default development flow is Plan -> Work -> Review.

1. Plan first when requirements are unclear or the task is larger than one small change.
2. Work on one scoped issue/change at a time.
3. Review the diff before considering the task complete.
4. Keep changes small, reversible, and testable.

## Architecture Rules
- Keep business logic separate from UI/framework glue.
- Prefer small public interfaces and deep modules.
- Do not introduce new dependencies without explaining why.
- Do not perform unrelated refactors while implementing an issue.
- Document meaningful architecture decisions in docs/adr/.

## Test Commands
- Unit tests: TODO
- Typecheck: TODO
- Lint: TODO
- Build: TODO

## Safety
- Do not delete files without explicit instruction.
- Do not change public behavior outside the active task.
- Ask before large rewrites, schema migrations, or dependency changes.
- If scope grows, stop and propose a new issue.
05

rules

.claude/rules/, CLAUDE.md'yi şişirmeden kalıcı talimatları modüler dosyalara bölmek için kullanılır. Rules, Claude'un bilmesi gereken davranış/proje kurallarıdır. Ama önemli nüans şu: path verilmemiş rule dosyaları session başında context'e girer; paths frontmatter kullanılan rule dosyaları ise Claude ilgili dosyalarla çalışırken yüklenir. Bu yüzden rules klasörü iyi bölünmezse session/context şişirebilir.

.claude/rules/ lets you split persistent instructions into modular files instead of growing one huge CLAUDE.md. Rules are behavior/project instructions Claude should know. The important nuance: rules without path scoping load at session start; rules with paths frontmatter load when Claude works with matching files. If you do not split and scope rules, they can bloat the session context.

.claude/rules/ · context-friendly example tree
.claude/
└─ rules/
   ├─ always.md              # tiny global rules; loads every session
   ├─ testing.md             # general test rules; loads every session if no paths
   ├─ frontend/
   │  └─ react.md            # path-scoped to React/TSX files
   └─ backend/
      └─ api.md              # path-scoped to API files
Frontmatter neden önemli? Rule dosyası markdown'dır; başına YAML frontmatter koyabilirsin. En pratik alan paths. paths yoksa rule genel kabul edilir ve session başında yüklenebilir. paths varsa Claude bu rule'u sadece eşleşen dosyalarla çalışırken context'e alır. Amaç: her şeyi baştan okutmak yerine Claude'un o an ihtiyaç duyduğu kuralı okutmak.
Why frontmatter matters: Rule files are markdown files with optional YAML frontmatter. The most useful field is paths. Without paths, the rule is global and may load at session start. With paths, Claude loads the rule when working with matching files. The goal is to avoid reading every rule up front and instead load the rule Claude needs for the current files.
.claude/rules/backend/api.md · path-scoped rule
---
paths:
  - "src/api/**/*.ts"
  - "app/api/**/*.ts"
  - "server/**/*.ts"
---

# API Rules

- Validate request input at the boundary.
- Return the shared error response shape.
- Keep database access behind the repository/service layer.
- Add or update tests for behavior changes.
.claude/rules/frontend/react.md · path-scoped UI rule
---
paths:
  - "src/**/*.tsx"
  - "app/**/*.tsx"
  - "components/**/*.tsx"
---

# React / UI Rules

- Prefer small, focused components.
- Keep server/client boundaries explicit.
- Do not introduce a new UI library without approval.
- Add accessible labels for interactive elements.

Pratik rule stratejisi: CLAUDE.md ve global rules minimumda kalsın. “Her işte bilmesi şart mı?” sorusunun cevabı hayırsa rule'u path-scoped yap veya skill'e taşı. Büyük checklist'leri global rule'a koyma; ilgili alana böl. Örneğin API standardı sadece src/api/**, UI standardı sadece **/*.tsx, test standardı sadece **/*.test.ts için yüklensin.
Practical rule strategy: Keep CLAUDE.md and global rules minimal. If the answer to “must Claude know this in every task?” is no, make the rule path-scoped or move it into a skill. Do not put large checklists into global rules. Split them by area: API rules for src/api/**, UI rules for **/*.tsx, test rules for **/*.test.ts.

settings.json

settings.json metinsel talimat değil, yapılandırmadır. İzinler, hook'lar, env bilgileri ve proje seviyesinde paylaşılması gereken teknik ayarlar burada durabilir.

settings.json is configuration, not prose instructions. Use it for permissions, hooks, env values, and shareable technical settings.

.claude/settings.json · example
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(npm run lint)",
      "Bash(npm run typecheck)",
      "Bash(npm run build)"
    ],
    "deny": [
      "Bash(rm -rf /)",
      "Bash(git push --force*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'File changed. Consider running tests.'"
          }
        ]
      }
    ]
  }
}
Best practice: Takımca paylaşılacak ayarlar .claude/settings.json içinde project scope'ta, kişisel izinler ve lokal path/env bilgileri .claude/settings.local.json içinde tutulmalıdır. settings.local.json git'e girmemeli; dosyayı Claude oluşturduysa gitignore'a ekler, elle oluşturduysan sen ekle.
Best practice: Shared team settings belong in project scope at .claude/settings.json; personal permissions and local paths/env values belong in .claude/settings.local.json. Keep settings.local.json out of git; Claude adds it to gitignore when it creates the file, but add it yourself if you create it manually.

commands

Claude Code'da commands derken iki farklı şeyi ayırmak gerekir: Claude Code'un kendi built-in slash command'ları ve eskiden .claude/commands/ altında tutulan custom command workflow'ları. Güncel setup anlatımında custom workflow'lar için tercih edilen yer skills'tir.

In Claude Code, commands means two different things: Claude Code's built-in slash commands and older custom command workflows that used to live under .claude/commands/. In a modern setup, custom reusable workflows should generally be implemented as skills.

Güncel ayrım: /usage, /context, /compact, /clear, /model gibi built-in command'lar hâlâ ayrı kavramdır. Fakat yeni bir custom workflow yazacaksan .claude/skills/<name>/SKILL.md kullanmak daha doğru anlatımdır. .claude/commands/ varsa backward compatibility/legacy olarak düşünülebilir.
Current distinction: Built-in commands such as /usage, /context, /compact, /clear, and /model are still separate. But for new custom workflows, prefer .claude/skills/<name>/SKILL.md. Treat .claude/commands/ as legacy/backward-compatible.
İsim çakışması notu: Bu dokümanda okunabilirlik için skill-backed command örnekleri /plan, /work, /review olarak gösterilir. Claude Code sürümünde aynı isimli built-in komutlarla çakışma yaşanırsa plugin namespace kullanmak (/agentic:plan) veya ekip standardına göre farklı bir isim seçmek daha güvenlidir.
Name collision note: For readability, this document shows skill-backed command examples as /plan, /work, and /review. If those names collide with built-in commands in your Claude Code version, use a plugin namespace such as /agentic:plan or choose a team-specific name.

skills

Skill, tekrar kullanılabilir prosedürdür ve slash-command entrypoint gibi çalışabilir. Güncel custom workflow'lar için önerilen ana yer .claude/skills/<name>/SKILL.md'dir. Bu dokümanda skill'leri ana kullanıcı arayüzü gibi ele alıyoruz: /plan, /work, /review.

A skill is a reusable procedure and can act as a slash-command entrypoint. The recommended place for modern custom workflows is .claude/skills/<name>/SKILL.md. In this reference, skills are the main user-facing workflow surface: /plan, /work, /review.

Discovery/path notu: Project/personal skill için beklenen yapı .claude/skills/plan/SKILL.md şeklindedir; .claude/skills/plan.md düz dosyası skill olarak yüklenmez. Komut olarak yazdığın ad klasör adından gelir: .claude/skills/plan/SKILL.md → /plan. Frontmatter’daki name alanı slash menüsündeki görüntü/display adını değiştirebilir; çoğu skill konumunda yazdığın komut adını değiştirmez. İstisna: plugin root SKILL.md kullanımı.
Discovery/path note: For project/personal skills, the expected layout is .claude/skills/plan/SKILL.md; a flat file like .claude/skills/plan.md is not loaded as a skill. The command you type comes from the directory name: .claude/skills/plan/SKILL.md → /plan. The frontmatter name field can change the display label shown in the slash menu, but in most skill locations it does not change the command you type. Exception: plugin root SKILL.md.
Küçük discovery notları: Aynı isimde hem .claude/commands/plan.md hem .claude/skills/plan/SKILL.md varsa skill önceliklidir. Claude mevcut skill klasörlerindeki değişiklikleri canlı yakalar; ama session başlarken .claude/skills/ hiç yoksa yeni klasörün izlenmesi için Claude'u restart etmek gerekebilir. Monorepo'da alt klasörlerdeki .claude/skills/ yapıları da ilgili dosyalarla çalışırken devreye girebilir.
Small discovery notes: If .claude/commands/plan.md and .claude/skills/plan/SKILL.md both exist, the skill takes precedence. Claude live-detects changes inside skill directories that existed when the session started; if .claude/skills/ did not exist at startup, restart Claude so it can watch the new directory. In monorepos, nested .claude/skills/ folders can become available when Claude works in those subdirectories.

Bu setup için önerilen model: /plan, /work, /review birer skill-backed command olsun. Agent'lar ise bu skill'lerin gerektiğinde başvuracağı uzman worker'lar olsun. Böylece katılımcı önce skill'i kopyalayıp kullanabilir; agent kısmını sonra detaylandırabilir.

Invocation kontrolü: Skill'ler iki şekilde devreye girebilir: kullanıcı doğrudan /skill-name ile çağırabilir veya Claude, skill açıklamasını uygun bulursa otomatik kullanabilir. Invocation control: Skills can be invoked in two ways: the user can call them directly with /skill-name, or Claude can invoke them automatically when their description matches the task. plan/SKILL.md
Gereksinim netleştirme ve issue çıkarma
Clarify requirements and create issues
skill
markdown
---
name: plan
description: Clarify requirements and turn broad work into small implementation issues.
disable-model-invocation: true
argument-hint: "<feature idea or task>"
---

# Plan Skill

Use this skill when the request is unclear, broad, risky, or larger than one small implementation step.

## User Request
$ARGUMENTS

## Inputs
- User request or feature idea
- Existing README / docs / issues / ADRs
- Relevant source files when needed

## Procedure
1. Read existing project context before proposing a plan.
2. Identify the goal, users, constraints, non-goals, and unknowns.
3. Ask only the most important clarification questions.
4. If deeper isolated research is useful, dispatch or ask for help from the planner agent.
5. Convert the work into small vertical-slice issues.
6. For each issue, include:
   - title
   - user story or behavior
   - acceptance criteria
   - test expectations
   - out of scope
   - suggested owner/agent

## Rules
- Do not implement code while planning.
- Do not create horizontal tasks like "create database layer" unless explicitly required.
- Prefer tracer-bullet issues that produce visible behavior.
- Separate facts, assumptions, and open questions.
work/SKILL.md
Tek scoped işi uygula
Implement one scoped task
skill
markdown
---
name: work
description: Implement one scoped issue with tests and minimal unrelated changes.
disable-model-invocation: true
argument-hint: "<issue file or task>"
---

# Work Skill

Use this skill when an issue is clear enough to implement.

## Active Issue / Task
$ARGUMENTS

## Inputs
- One issue or task
- Acceptance criteria
- Test commands
- Relevant source files

## Procedure
1. Restate the active scope in one short paragraph.
2. Inspect the relevant files.
3. Choose the smallest behavior to implement first.
4. Write or update a failing test when practical.
5. Implement the smallest change that makes the test pass.
6. Repeat until acceptance criteria are covered.
7. Use the worker agent for isolated implementation when the task is large enough to benefit from a fresh context.
8. Run relevant checks.
9. Summarize changed files, tests run, and remaining risks.

## Rules
- Work on one issue at a time.
- Do not perform unrelated refactors.
- Do not silently add dependencies.
- Do not broaden scope without stopping and asking.
- Keep changes reviewable.
review/SKILL.md
Diff review prosedürü
Diff review procedure
skill
markdown
---
name: review
description: Review a diff for correctness, scope, tests, architecture, and documentation.
disable-model-invocation: true
argument-hint: "<base branch, diff, issue, or PR URL>"
---

# Review Skill

Use this skill before marking work complete or before commit/PR.

## Inputs
- Git diff
- Active issue / acceptance criteria
- Test results
- Relevant docs

## Review Checklist
1. Does the diff satisfy the acceptance criteria?
2. Are there unrelated changes?
3. Are tests meaningful and behavior-focused?
4. Did typecheck/lint/build pass?
5. Is business logic placed in the right module?
6. Were docs updated when behavior, commands, or architecture changed?
7. Are there security, data, or migration risks?
8. If the diff is non-trivial, dispatch or ask for help from the reviewer agent.

## Output Format
- Summary
- Must fix
- Should fix
- Nice to have
- Tests run
- Final recommendation: approve / request changes / blocked

## Rules
- Be stricter with correctness than style.
- Do not approve untested behavior.
- Do not hide uncertainty.

# Diagnose Skill

## Procedure
1. Reproduce the failure or identify the smallest failing command.
2. Capture the exact error output.
3. List the most likely hypotheses.
4. Test one hypothesis at a time.
5. Add a regression test when possible.
6. Apply the smallest safe fix.
7. Run the nearest relevant tests, then broader checks if needed.

## Rules
- Do not rewrite large areas before understanding the failure.
- Do not suppress errors to make tests pass.
- Do not fix unrelated issues in the same pass.

## Procedure

agents

Agent, belirli bir role ait execution context'tir: system prompt, model, tool set, permission mode ve çıktı beklentisi burada tanımlanır. Bu setup'ta agent'lar tek başına da çağrılabilir; ama daha pratik model, /plan, /work, /review gibi skill'lerin gerektiğinde ilgili agent'lardan destek istemesidir.

An agent is an execution context for a role: system prompt, model, tool set, permission mode, and output expectations live here. In this setup, agents can be invoked directly, but the more practical model is for skills such as /plan, /work, and /review to request help from the relevant agents when useful.

Önemli: skills: alanı agent'ın bazı skill içeriklerini başlangıçta preload etmesi içindir. Yani agent daha işe başlamadan o skill'in tam içeriği context'ine eklenir. Bu, agent'ın sürekli bilmesi gereken convention/reference bilgileri için iyidir; her agent'a her şeyi preload etmek context'i şişirir. disable-model-invocation: true olan manuel-only skill'ler preload edilemez. Preload etmesen bile agent, Skill tool erişimi varsa ilgili project/user/plugin skill'lerini çalışma sırasında yine keşfedip çağırabilir.
Important: The skills: field preloads selected skill content into the agent at startup. In plain terms, the agent receives that skill's full text before it starts working. This is useful for conventions/reference knowledge the agent must always know, but preloading everything bloats context. Skills with disable-model-invocation: true cannot be preloaded. Even without preload, an agent can still discover and invoke relevant project/user/plugin skills during execution if it has access to the Skill tool.

hooks

Hook, belirli Claude Code lifecycle noktalarında otomatik çalışan komut/script'tir. Hook'lar LLM kararına bırakılmaması gereken küçük deterministik kontroller için iyidir.

A hook is a command/script that runs automatically at specific Claude Code lifecycle points. Hooks are good for small deterministic checks that should not depend on the LLM remembering them.

Hook tipiÖrnek kullanım
Hook typeExample use
PreToolUseRiskli bash komutunu engellemek veya onay istemek.
PostToolUseEdit sonrası test/format hatırlatmak veya otomatik kontrol çalıştırmak.
StopSession sonunda özet/checklist üretmek.
NotificationKullanıcı onayı veya dikkat gerektiren olayları bildirmek.
PreToolUseBlock risky bash commands or require approval.
PostToolUseRemind/run tests or formatting after edits.
StopProduce an end-of-session summary/checklist.
NotificationNotify when user attention/approval is needed.
hooks/remind-tests.py
#!/usr/bin/env python3
import json
import sys

payload = json.load(sys.stdin)
tool_name = payload.get("tool_name", "")

if tool_name in {"Write", "Edit", "MultiEdit"}:
    print("Reminder: file changed. Run the smallest relevant test before continuing.")

sys.exit(0)
settings.json · hook registration
{
  "permissions": {
    "allow": [
      "Bash(npm test)",
      "Bash(npm run lint)",
      "Bash(npm run typecheck)",
      "Bash(npm run build)"
    ],
    "deny": [
      "Bash(rm -rf /)",
      "Bash(git push --force*)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit",
        "hooks": [
          {
            "type": "command",
            "command": "echo 'File changed. Consider running tests.'"
          }
        ]
      }
    ]
  }
}
Hook best practice: Hook'ları sıkıcı ve güvenli tut. Büyük iş mantığı, karmaşık kararlar veya sık false-positive üretecek kontroller hook için iyi aday değildir.
Hook best practice: Keep hooks boring and safe. Big business logic, complex decisions, or noisy checks are poor hook candidates.

plugin

Plugin, skills/agents/hooks gibi tekrar kullanılabilir setup parçalarını tek projeden çıkarıp lokal veya GitHub üzerinde versiyonlanabilir hale getirir. Böylece her repo için baştan kopyalamak yerine aynı workflow tekrar kullanılabilir.

A plugin packages reusable setup pieces such as skills, agents, and hooks so they can be versioned locally or on GitHub and reused across projects.

Ne zaman lokal?

  • Kişisel workflow denemesi
  • Hızlı iterasyon
  • Henüz takıma hazır olmayan yapı

Ne zaman GitHub?

  • Takımca paylaşılacaksa
  • Versiyonlama gerekiyorsa
  • Review/PR sürecinden geçecekse

When local?

  • Personal workflow experiments
  • Fast iteration
  • Not ready for team adoption yet

When GitHub?

  • Shared with the team
  • Versioned releases are needed
  • Review/PR process is needed

context / token management

01
Session'ı küçük tut.
Bir session = bir faz veya bir küçük issue. Plan, Work ve Review uzun sürüyorsa ayrı session'lara böl.
Keep sessions small.
One session = one phase or one small issue. Split Plan, Work, and Review when they get long.
02
Kararı dosyaya yaz.
Önemli kararlar chat'te kalırsa kaybolur. Issue, ADR, README veya CONTEXT dosyasına al.
Write decisions to files.
Important decisions are lost if they only live in chat. Put them in issues, ADRs, README, or context docs.
03
Context şişince compact/clear kullan.
Önce aktif scope, kararlar, test sonuçları ve next step dosyaya yazılsın.
Use compact/clear when context grows.
First write active scope, decisions, test results, and next step into files.
04
Model seçimini iş tipine göre yap.
Plan ve review daha fazla reasoning ister; basit edit'ler daha düşük maliyetli modelle yapılabilir.
Choose models by task type.
Planning and review require more reasoning; simple edits may use cheaper models.

Do / Don't

Yap

Do

  • İşi küçük vertical slice'lara böl.
  • Agent'a test komutlarını açık ver.
  • Scope dışına çıkınca durdur.
  • Review'u sürecin parçası yap.
  • Tekrar eden prosedürü skill/plugin yap.
  • Split work into small vertical slices.
  • Give explicit test commands.
  • Stop when scope expands.
  • Make review part of the process.
  • Move repeated procedures into skills/plugins.

Yapma

Don't

  • Tek prompt ile komple feature yaptırma.
  • Testsiz AI kodunu merge etme.
  • CLAUDE.md'yi çöplüğe çevirme.
  • Hook'lara karmaşık karar mantığı koyma.
  • Agent'a sınırsız scope verme.
  • Do not ask for a complete feature in one prompt.
  • Do not merge untested AI-written code.
  • Do not turn CLAUDE.md into a junk drawer.
  • Do not put complex decision logic into hooks.
  • Do not give agents unlimited scope.
