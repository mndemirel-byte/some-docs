Paralel & Nested Subagents

Workshop 02'de subagent'ı izole bir execution environment olarak kurmuştuk. Bu bölümde iki yeni katman ekliyoruz: bağımsız subagent'ları aynı anda çalıştırmak (paralel) ve bir subagent'ın kendi subagent'ını çağırması (nested) — ne zaman işe yarar, ne zaman kontrolü elden kaçırır.

Workshop 02 established the subagent as an isolated execution environment. This session adds two layers: running independent subagents at the same time (parallel), and a subagent spawning its own subagent (nested) — when it helps, and when it quietly removes control from your hands.

01

Nereden Geliyoruz

Workshop 02'nin kuralı basitti: subagent daha akıllı bir agent değildir, izole bir execution environment'tır. Ana thread kararları ve gereksinimleri tutar; subagent gürültülü işi (arama, log, dosya taraması) kendi context'inde yapar ve yalnızca özetle geri döner.

Workshop 02's rule was simple: a subagent is not a smarter agent, it is an isolated execution environment. The main thread keeps decisions and requirements; the subagent absorbs noisy work (search, logs, file scans) in its own context and returns only a summary.

Bugün bu tek subagent modelini iki yönde genişletiyoruz: yatayda (birden fazla subagent'ı aynı anda çalıştırmak) ve dikeyde (bir subagent'ın kendi subagent'ını çağırması). İkisi de aynı temel mekanizmayı — izolasyon, sınırlı araç, özetlenmiş dönüş — farklı bir şekle sokuyor.

Today we extend that single-subagent model in two directions: horizontally (running several subagents at once) and vertically (a subagent spawning its own subagent). Both reshape the same underlying mechanism — isolation, constrained tools, summarized return.

Bugünün sorusu:Today's question: İzolasyonu koruyarak nasıl daha fazla iş paralelde yapabiliriz, ve ne zaman bu izolasyonu katmanlayıp (nested) riske değer?How do we do more work in parallel without losing isolation, and when is layering that isolation (nesting) worth the risk?
02

Paralel Subagents — Mental Model

Paralel çalıştırma, birbirine bağımlı olmayan görevleri aynı mesaj içinde birden fazla subagent çağrısı olarak göndermektir. Her subagent kendi izole context'inde aynı anda çalışır. Claude Code v2.1.198'den beri varsayılan davranış arka plan (background): her subagent — başarılı ya da hatalı — kendi bitişinde main thread'e bağımsız bir bildirim döner, diğerlerini beklemez. Sonuçların gerçekten tek seferde, hep birlikte gelmesi sadece run_in_background: false ile zorlanan senkron (foreground) modda geçerli.

Parallel execution means sending independent tasks as multiple subagent calls within the same message. Each subagent runs concurrently in its own isolated context. Since Claude Code v2.1.198, the default behavior is background: each subagent — success or failure — reports back to the main thread independently as it finishes, without waiting for the others. Results only truly arrive together, in one batch, when synchronous (foreground) mode is forced with run_in_background: false.

🟢 dispatch — aynı anda başlar🟠 her biri bağımsız bitince döner (varsayılan: arka plan)⏱ hepsini beklersen süre = en yavaş subagent
Ana fikir:Key idea: 3 bağımsız araştırmayı sırayla yapmak 3 tur sürer; paralel yaparsan (hepsini beklersen) 1 tur sürer — en yavaş olan kadar. Ama beklemek zorunda değilsin: varsayılan arka plan modunda erken biten/hata veren agent'ı görüp ona göre hareket edebilirsin, geri kalanları beklemeden.Three independent lookups done sequentially take three rounds; done in parallel (if you wait for all of them), they take one round — as long as the slowest. But you don't have to wait: in the default background mode you can see and act on an agent that finishes early or fails, without waiting for the rest.
Kaynak — versiyon notu:Source — version note: "Subagent'lar artık varsayılan olarak arka planda çalışır. run_in_background belirtilmeden yapılan bir Agent çağrısı arka plan subagent'ı başlatır... v2.1.198'den önce, run_in_background belirtilmeden yapılan çağrı subagent'ı senkron çalıştırırdı." (çeviri)"Subagents run in the background by default. An Agent tool call that omits run_in_background launches a background subagent... Before v2.1.198, omitting run_in_background ran the subagent synchronously." code.claude.com/docs/en/agent-sdk/subagents

04

Paralel: Nasıl Tetiklenir

Mekanik basit: paralellik, tek bir mesajda birden fazla Agent tool çağrısı göndermekten gelir. Ayrı mesajlarda art arda gönderilen çağrılar sıralı çalışır — paralel değil.

The mechanic is simple: parallelism comes from sending multiple Agent tool calls in a single message. Calls sent across separate messages run sequentially, not in parallel.

1. Bağımlılık kontrolü

1. Check for dependencies

B, A'nın çıktısına ihtiyaç duymuyor mu? Duyuyorsa paralel olamaz.

Does B need A's output? If so, it cannot run in parallel.

2. Açıkça iste

2. Ask explicitly

Claude paralellik konusunda temkinlidir; "N tanesini paralel çalıştır" de.

Claude is conservative about parallelism by default; explicitly say "run N of these in parallel."

3. Tek mesaj, çoklu blok

3. Single message, multiple blocks

Tüm Agent çağrıları aynı yanıtta yer almalı.

All Agent calls must be part of the same response.

Sık hata:Common mistake: "Şunu ve şunu paralel yap" demeden art arda iki subagent istemek — ikinci çağrı ilkinin sonucunu bekleyeceği için sıralı çalışır.Requesting two subagents back to back without saying "in parallel" — the second call ends up waiting for the first, running sequentially.

Bu repoda dene: frontend-dev ve data-dev zaten .claude/agents/ altında tanımlı, ikisi de dosya değiştirmiyor — bağımsız iki inceleme, paralel denemek için güvenli bir çift.

Try it in this repo: frontend-dev and data-dev are already defined under .claude/agents/, neither writes files — two independent reviews, a safe pair to test parallelism with.

06

Paralel: Dikkat Edilecekler

✓ Yap

✓ Do

  • Sadece birbirinden bağımsız görevleri paralelleştir.
  • Only parallelize tasks that are independent of each other.
  • Dosya yazan paralel agent'lar için worktree kullan.
  • Use worktrees for parallel agents that write files.
  • Kaç tane paralel istediğini açıkça söyle.
  • State explicitly how many parallel agents you want.

✕ Yapma

✕ Don't

  • Bağımlı görevleri paralel gönderme (B, A'yı bekliyorsa sıralı kalsın).
  • Don't send dependent tasks in parallel (if B waits on A, keep it sequential).
  • Onlarca subagent'ı aynı anda açma — sonuçlar toplu döner ve ana context'i şişirir.
  • Don't fan out to dozens of subagents at once — combined results still return to and inflate the main context.
Kaynak:Source: "While parallel subagents increase efficiency, be mindful that their combined results return to the main conversation and can impact context limits." — "While parallel subagents increase efficiency, be mindful that their combined results return to the main conversation and can impact context limits." — code.claude.com/docs/en/sub-agents
07

Nested Subagents — Mental Model

Nested, bir subagent'ın kendi Agent tool'unu kullanarak başka bir subagent çağırmasıdır. Ana thread yalnızca en üstteki subagent'ı görür; onun altında kaç katman olduğu ana thread'e hiç yansımaz.

Nesting means a subagent uses its own Agent tool to call another subagent. The main thread only sees the top-level subagent — whatever happens beneath it never surfaces to the main thread.

🧠 main thread sadece team-lead'i görür🔒 Agent tool'u olmayan asla nest edemez📏 max 5 seviye
08

Nested: Mekanizma

Nesting'i açan tek şey: bir subagent'ın kendi tools listesinde Agent (eski adıyla Task, alias hâlâ çalışıyor) olması. Yoksa o subagent hiçbir şey spawn edemez.

The single switch that enables nesting: whether a subagent's own tools list includes Agent (formerly Task, still a working alias). Without it, that subagent cannot spawn anything.

📏Derinlik limiti: 5Depth limit: 5
Ana thread'in altında en fazla 5 seviye; limitte olan subagent daha fazla nest edemez.Max 5 levels below the main agent; a subagent at the limit cannot spawn further.
📦Sadece üst özet dönerOnly the top summary returns
Ana thread'e sadece en üstteki subagent'ın özeti ulaşır, ara katmanlar görünmez.Only the top-level subagent's summary reaches the main thread; intermediate layers stay invisible.
🔁Devam eden agent derinliği korurResumed agents keep their depth
Arka planda devam eden bir subagent'ı resume etmek başlangıç derinliğini değiştirmez.Resuming a background subagent does not change its initial depth level.
Kaynak:Source: code.claude.com/docs/en/sub-agents, code.claude.com/docs/en/agent-sdk/subagents
09

Nested: Avantajlar

Hiyerarşik iş bölümü

Hierarchical delegation

Team-lead kendi alt görevlerini kendi yönetir; ana thread'i meşgul etmeden karmaşık işi bölebilir.

A team-lead manages its own subtasks; complex work gets broken down without occupying the main thread.

Dinamik orkestrasyon

Dynamic orchestration

Hangi alt-agent'ın ne zaman çağrılacağına lead karar verir; ana thread önceden planlamak zorunda kalmaz.

The lead decides which sub-agent to call and when; the main thread doesn't need to plan it upfront.

Yeniden kullanılabilir parçalar

Reusable pieces

developer gibi küçük agent'lar başka lead'ler tarafından da çağrılabilir.

Small agents like developer can be reused by other leads too.

10

Nested: Dezavantajlar & Riskler

Ara adımlar görünmez

Intermediate steps are invisible

Team-lead'in developer'a tam olarak ne söylediği ana thread'e hiç düşmez — debug etmek zorlaşır.

What the team-lead actually told the developer never reaches the main thread — debugging gets harder.

Tip kısıtlaması nested'de zayıflar

Type restriction weakens when nested

Agent(developer) gibi bir allowlist sadece ana thread'den yapılan ilk çağrıda geçerlidir; nested seviyede bu kısıtlama görmezden gelinir.

An allowlist like Agent(developer) only applies to the first call from the main thread; that restriction is ignored at the nested level.

Maliyet & gecikme katlanır

Cost & latency compound

Her seviye ek bir LLM turu; team-lead + 2 nested çağrı = en az 3 tur.

Every level adds an LLM round-trip; team-lead + 2 nested calls = at least 3 rounds.

Sert derinlik duvarı

Hard depth wall

Dikkatsiz tasarlanmış bir lead prompt'u, gerekmediği halde derinlik 5'e çarpıp sessizce durabilir.

A carelessly designed lead prompt can silently hit the depth-5 wall when it didn't need to.

Kaynak:Source: code.claude.com/docs/en/sub-agents — "type-specific restrictions in the Agent tool definition are ignored for nested spawns.""type-specific restrictions in the Agent tool definition are ignored for nested spawns."

Nested: Nasıl Açılır

Sadece lead'e Agent tool'unu ver; altındaki agent'lara verme.

Grant Agent only to the lead; withhold it from the agents beneath it.

Nested: Model Çözümleme — inherit Kimin Modelini Alır?

Senaryo: ana sohbet fable modelinde. Bir team-lead subagent model: opus ile açıkça çağrılıyor. Team-lead kendi içinde bir subagent daha çağırıyor, onun model alanı inherit. Bu üçüncü katman hangi modeli alır — ana sohbetin fable'ını mı, yoksa kendisini çağıran team-lead'in opus'unu mu?

Scenario: the main chat runs fable. A team-lead subagent is explicitly invoked with model: opus. The team-lead itself calls another subagent whose model field is inherit. Which model does that third layer get — the main chat's fable, or the calling team-lead's opus?

Resmi doküman ne diyor:What the official docs say: "If no specific model is defined, it defaults to the main conversation's model." — net, ama tek seviyeli senaryo (ana sohbet → subagent) için yazılmış."If no specific model is defined, it defaults to the main conversation's model." — clear, but written for the single-level case (main chat → subagent). code.claude.com/docs/en/sub-agents#choose-a-model
Çok-seviyeli zincirde belirsiz:Ambiguous for multi-level chains: Anthropic'in kendi dokümantasyon düzeltme sürecinde bile "main conversation" ve "parent session" birbirinin yerine kullanılıyor — ki bu ikisi 3 katmanlı bir zincirde aynı şey değil. Bu, açık kalan bir GitHub issue'da açıkça kabul ediliyor.Even in Anthropic's own documentation-fix process, "main conversation" and "parent session" get used interchangeably — which are not the same thing three levels deep. This is explicitly acknowledged in a GitHub issue that remains open. github.com/anthropics/claude-code/issues/19174
Pratik cevap — tahmin etme, doğrula:Practical answer — don't guess, verify: resolvedModel Agent SDK'nın alanı ama interaktif CLI session'da da yakalanabilir — bir PostToolUse hook, Agent tool'unu yakalar ve tool_response.resolvedModel içinde gerçek modeli verir. Aşağıda çalıştırılabilir tarif var.resolvedModel is an Agent SDK field, but it's also catchable in an interactive CLI session — a PostToolUse hook on the Agent tool exposes it in tool_response.resolvedModel. Runnable recipe below.
.claude/settings.json — canlı model logger
{
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Agent",
        "hooks": [
          { "type": "command", "command": "jq -c '{caller: (.agent_type // \"main\"), subagent: .tool_input.subagent_type, model: .tool_response.resolvedModel}' >> /tmp/subagent-models.log" }
        ]
      }
    ]
  }
}

İkinci bir terminalde tail -f /tmp/subagent-models.log aç, sonra normal chat'te tech-lead'i çalıştır. Hook input şemasındaki agent_type alanı "hook bir subagent içindeyken mevcut" olduğu için, nested çağrının hangi agent tarafından tetiklendiği de log'a düşer: önce {"caller":"main","subagent":"tech-lead","model":"opus"}, sonra tech-lead'in kendi nested çağrısı {"caller":"tech-lead","subagent":"frontend-dev","model":"…"}.

Open a second terminal with tail -f /tmp/subagent-models.log, then run tech-lead in the normal chat. Since the hook input's agent_type field is "present when the hook fires inside a subagent," the log also shows which agent triggered the nested call: first {"caller":"main","subagent":"tech-lead","model":"opus"}, then tech-lead's own nested call {"caller":"tech-lead","subagent":"frontend-dev","model":"…"}.

İki ön koşul:Two prerequisites: resolvedModel Claude Code ≥2.1.174 gerektirir (claude --version ile kontrol et). CLAUDE_CODE_SUBAGENT_MODEL set ediyorsan tüm sonuçları sessizce tek modele sabitler, transcript'te sinyal vermez — demodan önce echo $CLAUDE_CODE_SUBAGENT_MODEL ile boş olduğunu doğrula.resolvedModel requires Claude Code ≥2.1.174 (check with claude --version). If CLAUDE_CODE_SUBAGENT_MODEL is set, it silently pins every result to one model with no signal in the transcript — verify it's empty with echo $CLAUDE_CODE_SUBAGENT_MODEL before the demo.
Belirsizliği tamamen kaldırmak istersen:To remove the ambiguity entirely: CLAUDE_CODE_SUBAGENT_MODEL ortam değişkenini set et — zincirdeki her seviyeye, "main conversation" ne anlama gelirse gelsin, tek bir modeli zorlar.Set the CLAUDE_CODE_SUBAGENT_MODEL environment variable — it forces one model across every level of the chain regardless of what "main conversation" resolves to.

TL;DR

Paralel = tek mesaj.Parallel = one message.

Bağımsız görevleri aynı mesajda birden fazla Agent çağrısı olarak gönder.

Send independent tasks as multiple Agent calls within the same message.

Nested = Agent tool'u ver ya da alma.Nested = grant or withhold the Agent tool.

Bir subagent'ın nest edip edemeyeceğini tek başına tools listesi belirler.

Whether a subagent can nest is decided entirely by its tools list.

Sonuç her zaman özetlenir.Results always get summarized.

Ne kadar paralel ya da derin olursa olsun, ana thread'e sadece özet döner.

No matter how parallel or deep, only a summary returns to the main thread.

Limitleri unutma.Remember the limits.

Derinlik 5, birleşik context şişmesi ve maliyet katlanması — hepsi gerçek sınırlar.

Depth 5, combined context bloat, and compounding cost — all real limits.

Son kural:Final rule: Ara iş görünür kalmalıysa main thread. Ara iş gürültüyse subagent. Gürültü katmanlıysa (lead + alt işçiler) nested.If intermediate work must stay visible, use the main thread. If it's noise, use a subagent. If the noise is layered (lead + workers), nest.
