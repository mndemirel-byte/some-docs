Proje Tanımı: URL Shortener

Örnek projemiz basit bir URL kısaltma servisi. Yeterince küçük (bir yazıda tamamlanabilir) ama yeterince derin (database, API, redirect mantığı, analytics) — skill'lerin her birini göstermek için ideal senaryo.

Özellikler

  • Kullanıcı uzun URL verir, sistem kısa link döndürür
  • Kısa link ziyaretinde orijinal URL'ye yönlendirme
  • Her yönlendirme kayıt altına alınır (tıklama, tarih)
  • Basit dashboard tıklama istatistiklerini gösterir

Repo oluşturma

bash
mkdir url-shortener && cd url-shortener
git init
gh repo create url-shortener \
  --public --source=. --push

PRD Oluştur

/to-prd · Grilling tamamlanınca Zorunlu

/to-prd sizi tekrar interview etmez. Konuşma bağlamındaki her şeyi (grilling kararları, CONTEXT.md, ADR'lar) sentezleyerek bir PRD üretir ve doğrudan GitHub Issues'a publish eder.

Terminal çıktısı — /to-prd
claude — url-shortener
> /to-prd

Claude: Konuşma bağlamını ve domain doc'ları sentezliyorum...

Repo'yu inceliyorum — mevcut seam'ler:
  - Henüz kod yok, sıfırdan başlıyoruz.
  - Önerilen test seam'leri:
    1. LinkService (slug üretimi + persistence)
    2. RedirectHandler (slug → URL çözümleme + click kaydı)
    3. AnalyticsService (click count hesaplama)

Bu seam'ler doğru mu?
Siz: Doğru, devam et.

Claude: PRD'yi GitHub Issues'a publish ediyorum...

✓ Issue #1 oluşturuldu: "PRD: URL Shortener v1"
  Label: ready-for-agent

PRD içeriği:
  ## Problem Statement
  Kullanıcıların uzun URL'leri kısa linklere dönüştürmesi
  ve tıklama istatistiklerini görmesi gerekiyor.

  ## User Stories
  1. Uzun URL verip kısa link almak istiyorum.
  2. Kısa link ziyaretçisi olarak yönlendirilmek istiyorum.
  3. Toplam tıklama sayısını görmek istiyorum.
  4. Tıklama geçmişini (tarih, referrer) görmek istiyorum.

  ## Implementation Decisions
  - Slug: 6 karakter rastgele alfanumerik (ADR-0001)
  - Her submission yeni slug üretir (ADR-0001)
  - Click kayıtları individual (ADR-0002)
  - Auth yok v1'de (ADR-0003)
  - API-only, UI yok (ADR-0004)
  - Stack: Node.js + TypeScript + SQLite

  ## Testing Decisions
  - Seam 1: LinkService — unit test
  - Seam 2: RedirectHandler — integration test
  - Seam 3: AnalyticsService — unit test
  - E2E: create link → visit → check analytics

  ## Definition of Done
  Testler ✓ | Typecheck ✓ | Build ✓

/to-prd'nin önemli farkı: "Testing Decisions" bölümü sadece "unit test yazılacak" demez — test sınırlarını (seam) açıkça tanımlar. Bu, /tdd adımında agent'ın testleri nereye koyacağını ve neyi test edeceğini bilmesini sağlar.

HITL vs AFK ayrımı: Her issue "HITL" (Human-in-the-Loop) veya "AFK" olarak etiketlenir. AFK issue'lar agent'ın tek başına tamamlayabileceği, iyi tanımlı işlerdir. HITL issue'lar mimari karar veya insan müdahalesi gerektirir. Bu projede tüm issue'lar AFK — çünkü kararlar grilling sırasında alındı ve PRD'de belgelendi.

TDD ile İmplementasyon

/tdd · Her issue için Zorunlu

/tdd, Red-Green-Refactor döngüsüyle çalışır. Horizontal slicing yapmaz — "önce tüm testleri yaz, sonra tüm kodu yaz" demez. Bunun yerine vertical slice: bir test yaz → o testi geçir → sonraki test. Her döngüde agent önceki döngüden öğrenir.

Terminal çıktısı — /tdd #2
claude — url-shortener
> /tdd #2

Claude: Issue #2: "Create short link and return slug"

Acceptance criteria:
  POST /links body: { url } → response: { slug, url, createdAt }
  Slug 6 karakter alfanumerik olmalı
  Link veritabanına kaydedilmeli

CONTEXT.md'den domain dili:

  link: bir URL + slug çifti

/tdd'nin Temel Prensipleri

1 · Horizontal slicing yasak

"Önce 5 test yaz, sonra 5 implementation" yapmaz. Her test-implementation çifti bir vertical slice'tır.

2 · Integration-style testler

Internal mock'lar yerine public interface üzerinden test yazılır. "checkout calls paymentService" değil, "user can checkout" test edilir.

3 · Deep module hedeflenilir

Küçük interface, zengin implementation. Test sınırı = modül sınırı. Refactor aşamasında bu kontrol edilir.

4 · Mocking sadece system boundary

Kendi modüllerini mock'lama. Sadece harici bağımlılıkları (database, API, filesystem) mock'la.

Mimariyi İyileştir

/improve-codebase-architecture · Her 3-5 issue'da bir Opsiyonel ama önerilir

Bu skill, CONTEXT.md'deki domain dilini ve ADR'ları kullanarak kod tabanını analiz eder. Shallow module'ları tespit eder ve deepening önerileri sunar. Farkı kodu sadece yapısal olarak değil, domain dili bağlamında analiz etmesidir.

Terminal çıktısı — /improve-codebase-architecture
claude — url-shortener
> /improve-codebase-architecture

Claude: CONTEXT.md'den: slug, link, click, click count
ADR'lardan: unique slug per submission, individual click records

Tespit edilen deepening fırsatları:

1. [Strong] ClickRecorder + ClickCounter birleştirilebilir
   → AnalyticsService olarak tek deep module

   Problem: İki ayrı modül aynı click tablosuna erişiyor.
   Interface'leri birlikte neredeyse tüm click mantığını kapsıyor.

   Deletion test: ClickCounter silinsek, aynı mantık
   AnalyticsService caller'larına dağılır.

   Before: ClickRecorder + ClickCounter (2 modül, 2 interface)
   After:  AnalyticsService (1 modül, 2 public method)

2. [Worth exploring] SlugGenerator ayrı modül mü olmalı?
   Problem: Şu an LinkService içinde ama sadece bir fonksiyon.
   Deletion test: Silinse complexity kaybolur, yayılmaz.
   Öneri: Şimdilik LinkService içinde kalsın.

Uygulamak istediğiniz önerileri seçin.

İhtiyaç Halinde: Yardımcı Skill'ler

/diagnose — Yapılandırılmış Debugging

Zor bug'larda — agent'ın veya sizin çözemediğiniz durumlarda

Loop sırası: feedback loop kur → reproduce et → minimize et → hipotez kur → instrument et → fix et → regression test yaz. En kritik adım ilkidir: agent deterministic, hızlı ve otomatik çalıştırılabilir bir feedback loop kurmadan ilerlemez.

Örnek çıktı
claude — /diagnose
> /diagnose Redirect endpoint bazen 404 dönüyor
  ama slug database'de var.

Claude: Phase 1 — Feedback loop kuruyorum...
Bug'ı güvenilir şekilde reproduce edecek bir test yazıyorum...

[failing test → bug reproduce → minimize → hipotez
→ fix → regression test eklendi]

/zoom-out — Üst Düzey Bakış

Tanımadığınız bir kod alanına girdiğinizde

Agent'a belirli bir dizin veya modül hakkında CONTEXT.md'deki domain diliyle üst düzey bakış kazandırır: hangi modüller bağımlı, kim çağırıyor, hangi seam'ler var.

claude — /zoom-out
> /zoom-out src/analytics/

Claude: Analytics modülü, click kayıtlarını sorgulayan
servis katmanıdır.

  LinkService → (link oluşturur)
  RedirectHandler → (click kaydeder) → ClickRepository
  AnalyticsService → (click'leri okur) ← ClickRepository
                   → (link meta verisini okur) ← LinkRepository

Caller'lar: GET /links/:slug/stats endpoint'i

/prototype — Tasarım Kararı Doğrulama

Mimari konusunda kararsızlık varsa — "bu strateji doğru mu?" gibi soruları somutlaştırmak için

Throwaway prototype (terminal script, minimal UI veya log analizi) ile tasarım kararını veri ile doğrular. Sonucu ADR olarak belgeleyebilir.

claude — /prototype
> /prototype Slug collision handling stratejisini test
  etmek istiyorum — retry mi, sequential fallback mı?

Claude: Bu bir logic sorusu — terminal script oluşturuyorum.

[10,000 slug üretir, collision oranını ölçer,
retry vs sequential stratejilerini karşılaştırır]

Sonuç: 6 karakter alfanumerik ile 1M slug'da collision
oranı %0.001. Retry stratejisi yeterli, sequential
fallback gereksiz karmaşıklık.
