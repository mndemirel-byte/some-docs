04

Things You Must Always Do

1. Break every job into small pieces

Instead of telling AI "rewrite this whole module," tell it to "complete this small vertical slice with these acceptance criteria."

2. Watch token and context usage

The model's performance drops over long sessions. Signs of declining quality: repeated mistakes, forgetting decisions it made earlier, producing irrelevant code. When you see these signs, clear the session and continue with fresh context. If the tool supports it, make token usage visible.

3. Make the codebase readable for AI

Well-named modules, clean interfaces, clear test boundaries, an up-to-date README, and local development commands directly increase agent success.

4. Keep PRD and issue artifacts as files

Decisions left in conversation with AI get lost. Decisions should be made permanent in the repository as Markdown issues, PRDs, ADRs, or test plans.

5. Give AI the test commands explicitly

text — TypeScript/JS
After implementation, run:
- npm test
- npm run typecheck
- npm run lint
- npm run build
text — Python
After implementation, run:
- pytest
- ruff check .
- mypy .

6. Never skip review

As AI produces more code, the review burden grows. Human review and QA preserve quality and the engineering instinct we call "taste" — evaluating not just whether the code works, but whether it was designed correctly, is maintainable, and meets team standards.

05

Things You Must Never Do

1. Don't try to build "an entire feature in one prompt"

It bloats context, grows scope, and makes the model harder to control.

2. Don't just fix the spec and move on without reading the code

This approach disconnects the developer from the code. Code is still the primary reality. Spec-first is correct in areas like API contracts and migration plans — but after writing the spec, you still need to read and understand the resulting code.

3. Don't merge untested AI code

Code AI produces may compile but might not behave correctly. It's not trustworthy without tests, typecheck, and a build.

4. Don't blindly follow a horizontal phase plan

A plan that goes database only → then API → then frontend delays feedback. Vertical slices should be preferred.

5. Don't create huge CLAUDE.md / system prompt files

Files like CLAUDE.md and .cursorrules should be kept small. If the starting context is too large, the model starts burning through its effective attention capacity before it even begins work.

6. Don't leave stale documents lying around the repo

Old PRDs or closed decision documents can mislead AI. PRDs should be closed and archived after implementation.

The Recommended AI Coding Playbook

For a simple feature
  • 1Read the brief.
  • 2Interrogate me, extract the missing decisions.
  • 3Produce a PRD.
  • 4Split the PRD into vertical slice issues.
  • 5Implement the first issue using TDD.
  • 6Run test / typecheck / build.
  • 7Write a summary.
  • 8I will review it.
For a larger feature
  • 1A grilling session with domain expert + developer + AI.
  • 2Produce a PRD.
  • 3Build a prototype if a technical spike is needed.
  • 4Split the PRD into Kanban issues.
  • 5Order the issues as a dependency graph.
  • 6Hand independent issues to parallel agents.
  • 7Each agent works in its own branch / worktree / sandbox.
  • 8Make test and build signals mandatory.
  • 9Human review before merge.
  • 10Close the PRD / issue, archive the document.

Areas of Responsibility for Teams

The areas of responsibility below don't need to be separate roles. On a small team, one person can own multiple areas. What matters is that every area is consciously owned by someone.

Area of ResponsibilityScopeWho can own it?
Requirements and domain knowledgeEdge cases, user behavior, business rulesProduct manager, domain expert, senior developer
Code quality and implementationModule design, writing code, testsDeveloper
Architecture decisionsModule boundaries, dependency management, deep module designSenior developer, architect
AI agent managementIssue-based task distribution, agent configuration, AFK conditionsDeveloper, tech lead
ReviewCode quality, security, maintainabilityAnother developer, senior developer
QA and test strategyTest scenarios, regression, e2e verificationDeveloper, QA engineer
OrchestrationIssue order, dependency graph, parallel agent coordinationTech lead, senior developer

Small Team Examples

A team of 2

Developer A: requirement clarification, implementation, agent management, and QA.
Developer B: review, architecture decisions, and orchestration.
Roles can rotate.

Solo developer

All areas fall on one person. In this case it's useful to use the AI agent as a "second pair of eyes" — having it review its own code in a different session, asking it to suggest missing tests, and so on.

An Example AI Coding Session Flow

An example showing how all the stages turn into a real conversation in practice. Scenario: adding a simple points system to an education platform.

Developer

Read this feature brief. Don't write code. Interrogate me first.

AI
  • Which user segment is this feature for?
  • What's the success metric?
  • Will existing data be processed retroactively?
  • Where will the UI appear?
  • What are the edge cases?
Developer

Gives the answers.

AI

Produces a PRD → docs/prd/gamification-points.md

Developer

Split the PRD into vertical slice issues.

AI
  • Issue 01: Minimal end-to-end flow
  • Issue 02: Edge case handling
  • Issue 03: Admin visibility
  • Issue 04: Migration / backfill
  • Issue 05: Tests and cleanup
Developer

Implement Issue 01 using TDD. Don't go outside scope.

AI

Writes tests → implements → runs the tests → gives a summary.

Developer

Reviews, asks for changes, or merges.

10

The Most Important Best Practices

1Don't have AI write code directly; ask it to interrogate you first.
2Aim for shared understanding, not a plan.
3Produce a PRD, but don't treat it as living truth; the code is the truth.
4Split issues as vertical slices.
5Give the agent small, independent, testable work.
6Use TDD; have AI write tests first.
7Keep context small; don't rely on long sessions.
8When using sub-agents, keep the parent context clean.
9Build a deep module architecture; avoid the shallow dependency soup.
10Make human review and QA a mandatory part of the process.
11AFK coding is not unconditionally safe; branch isolation, an iteration limit, and diff review are mandatory.
11

Short Summary

The essence of AI coding isn't "knowing how to write a prompt." The real issue is this:

Getting AI to do the right work, at the right size, with the right context, inside the right feedback loop.

That's why a successful AI coding process can be reduced to this formula:

Align­ment
→
PRD
→
Vertical Slice Issues
→
TDD Impl.
→
Auto Checks
→
Human Review
→
Merge

AI coding doesn't automatically turn an undisciplined developer into a good one. On the contrary, it amplifies the lack of discipline. But combined with good software engineering practices, it becomes a powerful production model that ships well-planned, testable, small, independent pieces of work very quickly.

Taken together with Part 1, this framework forms the foundation for building an agentic software delivery workflow regardless of which language or tool you choose.
