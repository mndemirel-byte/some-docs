Building a Project from Scratch with Matt Pocock Skills

Pocock's open-source skill set is a collection of structured prompt templates added to Claude Code as slash commands. Their purpose isn't to speed up the agent — it's to impose discipline: forcing thought before code, building a test feedback loop, protecting architecture, and documenting decisions. In this piece, we walk through the complete flow step by step using a URL Shortener example.

Prerequisites and Setup

Required tools

  • Claude Code — npm install -g @anthropic-ai/claude-code
  • Node.js v18+ — for the skill installer and the example project
  • Git + GitHub — skills integrate with GitHub Issues
  • GitHub CLI (gh) — needed for writing to the issue tracker

Installing the gh CLI

bash
# macOS
brew install gh

# Linux
sudo apt install gh

# Authenticate
gh auth login
powershell
# with winget
winget install --id GitHub.cli

# or with Scoop
scoop install gh

# Authenticate
gh auth login

Installing the Skills

Pocock's skills install with a single command. It asks which skills you want and which agent (Claude Code, Cursor, etc.) to install them for:

bash
npx skills@latest add mattpocock/skills

During installation, choose which skills to install. Be sure to select /setup-matt-pocock-skills — the other skills depend on its output. Choose Claude Code as the target agent. The skills are installed into your project's .claude/ directory.

bash — start the project
cd your-project
claude
# Commands like /grill-with-docs, /tdd, /to-prd are now active
02

Project Definition: URL Shortener

Our example project is a simple URL shortening service. Small enough to finish in one piece, but deep enough (database, API, redirect logic, analytics) to be an ideal scenario for showcasing each skill.

Features

  • The user provides a long URL; the system returns a short link
  • Visiting the short link redirects to the original URL
  • Every redirect is recorded (click, date)
  • A simple dashboard shows click statistics

Creating the repo

bash
mkdir url-shortener && cd url-shortener
git init
gh repo create url-shortener \
  --public --source=. --push
powershell
mkdir url-shortener; cd url-shortener
git init
gh repo create url-shortener `
  --public --source=. --push

1

Interrogate the Idea and Establish Domain Language

/grill-with-docs · Before every new feature Mandatory

/grill-with-docs relentlessly interviews you — but while doing so it does two extra things: (1) it builds/updates the project's domain language (CONTEXT.md), and (2) it documents architectural decisions as ADRs under docs/adr/.

Terminal output — /grill-with-docs
claude — url-shortener
> /grill-with-docs We're going to build a simple URL shortener.
  User gives a URL, gets back a short link. Clicks are
  counted and shown on a dashboard.

Claude: I won't produce a plan right away — there are things I need
to clarify first.

Question 1/N: What format will the short URLs use?
A random string (abc123), or a sequential number?
My suggestion: 6-character random alphanumeric — low
collision risk and readable URLs.

You: Random 6 characters, alphanumeric.

Claude: [Adding to CONTEXT.md]
  slug — The 6-character random alphanumeric identifier
  in the short URL. E.g.: abc123 → example.com/abc123

Question 2/N: If the same URL is shortened a second time, what happens?
Should a new slug be generated, or should the existing slug be returned?
My suggestion: Generate a new slug every time — from an
analytics standpoint, each campaign/share may want its own link.

You: A new slug every time.

Claude: [Creating docs/adr/0001-unique-slug-per-submission.md]
  # New Slug for Every Submission of the Same URL
  Decision: Every URL submission generates a new slug.
  Why: To track clicks from different sources separately.
  Alternative: Idempotent — rejected because it loses
  analytics granularity.

Question 3/N: What information will be stored per click?
My suggestion: Each click as a separate record
(timestamp, referrer, user-agent).

You: Each click as a separate record.

Claude: [Adding to CONTEXT.md]
  click — A single HTTP request to a slug.
  Timestamp, referrer, and user-agent are recorded.

(... 8-10 more questions: auth, rate limiting, can a slug be
deleted, dashboard content, API-only or not, tech stack ...)

Claude: Files created/updated:

CONTEXT.md:
  slug, click, link, click count, dashboard terms
  Relationships between terms (link has many clicks)

docs/adr/:
  0001-unique-slug-per-submission.md
  0002-individual-click-records.md
  0003-no-auth-for-v1.md
  0004-api-first-no-ui-for-v1.md

The Value of This Step

Shared Understanding
You and the agent understand the same thing using the same words
CONTEXT.md
Variable and function names will follow the domain language
ADRs
Decisions are documented; the same questions won't be asked in a new session
2

Produce a PRD

/to-prd · Once grilling is done Mandatory

/to-prd doesn't interview you again. It synthesizes everything in the conversation context (grilling decisions, CONTEXT.md, ADRs) into a PRD and publishes it directly to GitHub Issues.

Terminal output — /to-prd
claude — url-shortener
> /to-prd

Claude: Synthesizing the conversation context and domain docs...

Inspecting the repo — current seams:
  - No code yet, starting from scratch.
  - Suggested test seams:
    1. LinkService (slug generation + persistence)
    2. RedirectHandler (slug → URL resolution + click recording)
    3. AnalyticsService (click count calculation)

Are these seams correct?
You: Correct, go ahead.

Claude: Publishing the PRD to GitHub Issues...

✓ Issue #1 created: "PRD: URL Shortener v1"
  Label: ready-for-agent

PRD content:
  ## Problem Statement
  Users need to be able to turn long URLs into shareable
  short links and see click statistics.

  ## User Stories
  1. I want to give a long URL and get a short link.
  2. As a short-link visitor, I want to be redirected.
  3. I want to see the total click count.
  4. I want to see click history (date, referrer).

  ## Implementation Decisions
  - Slug: 6-character random alphanumeric (ADR-0001)
  - Every submission generates a new slug (ADR-0001)
  - Click records are individual (ADR-0002)
  - No auth in v1 (ADR-0003)
  - API-only, no UI (ADR-0004)
  - Stack: Node.js + TypeScript + SQLite

  ## Testing Decisions
  - Seam 1: LinkService — unit test
  - Seam 2: RedirectHandler — integration test
  - Seam 3: AnalyticsService — unit test
  - E2E: create link → visit → check analytics

  ## Definition of Done
  Tests ✓ | Typecheck ✓ | Build ✓

What's distinctive about /to-prd: the "Testing Decisions" section doesn't just say "unit tests will be written" — it explicitly defines test boundaries (seams). This is what lets the agent know where to put tests and what to test during the /tdd step.

3

Split the PRD into Issues

/to-issues · Once the PRD is approved Mandatory

/to-issues splits the PRD into vertical slice (tracer bullet) issues. Every issue cuts through all layers vertically. It doesn't do horizontal splitting (all the database first, then all the API).

Terminal output — /to-issues
claude — url-shortener
> /to-issues #1

Claude: Reading PRD #1... Loading domain language from CONTEXT.md...

Suggested vertical slice breakdown:

1. "Create short link and return slug"
   Type: AFK | Blocked by: none | User stories: #1

2. "Redirect slug to original URL and record click"
   Type: AFK | Blocked by: #1 | User stories: #2

3. "Get click count for a link"
   Type: AFK | Blocked by: #2 | User stories: #3

4. "Get click history with timestamps and referrers"
   Type: AFK | Blocked by: #2 | User stories: #4

5. "Handle edge cases: expired slug, invalid slug, collision"
   Type: AFK | Blocked by: #1, #2

Is the granularity appropriate? Are the dependencies correct?
You: Looks good, create them.

Claude: Publishing the issues to GitHub...
✓ Issue #2: Create short link and return slug
  Label: ready-for-agent
✓ Issue #3: Redirect slug to original URL and record click
  Label: ready-for-agent | Blocked by: #2
✓ Issue #4: Get click count for a link
  Label: ready-for-agent | Blocked by: #3
✓ Issue #5: Get click history with timestamps and referrers
  Label: ready-for-agent | Blocked by: #3
✓ Issue #6: Handle edge cases
  Label: ready-for-agent | Blocked by: #2, #3

HITL vs. AFK split: every issue is labeled "HITL" (Human-in-the-Loop) or "AFK." AFK issues are well-defined work the agent can complete on its own. HITL issues require an architectural decision or human intervention. In this project all issues are AFK — because the decisions were made during grilling and documented in the PRD.

4

Implementation with TDD

/tdd · For every issue Mandatory

/tdd works through the Red-Green-Refactor loop. It doesn't do horizontal slicing — it never says "write all the tests first, then all the code." Instead it's vertical slice: write one test → make it pass → next test. The agent learns from the previous loop in each cycle.

Terminal output — /tdd #2
claude — url-shortener
> /tdd #2

Claude: Issue #2: "Create short link and return slug"

Acceptance criteria:
  POST /links body: { url } → response: { slug, url, createdAt }
  Slug must be 6 alphanumeric characters
  Link must be saved to the database

Domain language from CONTEXT.md:
  slug: a 6-character random alphanumeric identifier
  link: a URL + slug pair

─── RED: First test ───

Creating tests/link-service.test.ts:

  describe("LinkService", () => {
    it("should create a link with a 6-char alphanumeric slug", () => {
      const link = createLink("https://example.com");
      expect(link.slug).toMatch(/^[a-z0-9]{6}$/);
      expect(link.url).toBe("https://example.com");
    });
  });

npm test → FAIL ✗ (createLink doesn't exist yet)

─── GREEN: Minimal implementation ───

Creating src/link-service.ts:

  export function createLink(url: string) {
    const slug = generateSlug();
    // ... persist + return
  }

npm test → PASS ✓

─── RED: Next test ───

  it("should create unique slugs for the same URL", () => {
    const link1 = createLink("https://example.com");
    const link2 = createLink("https://example.com");
    expect(link1.slug).not.toBe(link2.slug);
  });

npm test → PASS ✓

(... the RED-GREEN loop continues: API endpoint test,
validation test, one test → one implementation each time)

─── REFACTOR ───

generateSlug() and persistence logic live in the same function.
Per the deep module principle, I'm restructuring LinkService.
npm test → PASS ✓ (all tests still pass)
npm run typecheck → PASS ✓
npm run build → PASS ✓

Implementation Summary:
- src/link-service.ts (new)
- src/routes/links.ts (new)
- tests/link-service.test.ts (3 tests)
- tests/links-api.test.ts (2 tests)

The Core Principles of /tdd

1 · No horizontal slicing

It never does "write 5 tests first, then 5 implementations." Every test-implementation pair is a vertical slice.

2 · Integration-style tests

Tests are written against the public interface rather than internal mocks. Not "checkout calls paymentService," but "user can checkout."

3 · Targets deep modules

Small interface, rich implementation. Test boundary = module boundary. This is checked during the refactor stage.

4 · Mocking only at system boundaries

Don't mock your own modules. Only mock external dependencies (database, API, filesystem).

Issue Management

/triage · When issues pile up Optional

/triage manages issues with a state machine. You can skip it on small projects or solo work. Every issue is in one of these states:

unlabeled → needs-triage → ready-for-agent / ready-for-human / needs-info → needs-triage / wontfix
Terminal output — /triage
claude — url-shortener
> /triage Show me the issues that need attention

Claude: Scanning the issue tracker...

ready-for-agent (can be picked up):
  #3 Redirect slug to original URL — blocked by #2
  #4 Get click count — blocked by #3
  #5 Get click history — blocked by #3
  #6 Handle edge cases — blocked by #2, #3

needs-triage: (none)

Suggested action: Since issue #2 is done, #3 is no
longer blocked. You can proceed with #3.

You: Pick up #3 and implement it with /tdd.

Improve the Architecture

/improve-codebase-architecture · Every 3-5 issues Optional but recommended

This skill analyzes the codebase using the domain language in CONTEXT.md and the ADRs. It detects shallow modules and offers deepening suggestions. What sets it apart is that it analyzes the code not just structurally, but in the context of the domain language.

Terminal output — /improve-codebase-architecture
claude — url-shortener
> /improve-codebase-architecture

Claude: From CONTEXT.md: slug, link, click, click count
From ADRs: unique slug per submission, individual click records

Detected deepening opportunities:

1. [Strong] ClickRecorder + ClickCounter could be merged
   → into a single deep module, AnalyticsService

   Problem: Two separate modules access the same click table.
   Their interfaces together cover nearly all click logic.

   Deletion test: if ClickCounter were deleted, the same
   logic would spread across AnalyticsService's callers.

   Before: ClickRecorder + ClickCounter (2 modules, 2 interfaces)
   After:  AnalyticsService (1 module, 2 public methods)

2. [Worth exploring] Should SlugGenerator be its own module?
   Problem: Currently inside LinkService, but it's just one function.
   Deletion test: if removed, complexity disappears, doesn't spread.
   Recommendation: Leave it inside LinkService for now.

Select which suggestions you'd like to apply.

As Needed: Helper Skills

/diagnose — Structured Debugging

For hard bugs — when neither the agent nor you can solve it

Loop order: build a feedback loop → reproduce → minimize → form a hypothesis → instrument → fix → write a regression test. The most critical step is the first one: the agent doesn't proceed until it has a deterministic, fast, automatically runnable feedback loop.

Example output
claude — /diagnose
> /diagnose The redirect endpoint sometimes returns 404
  even though the slug exists in the database.

Claude: Phase 1 — Building a feedback loop...
Writing a test that reliably reproduces the bug...

[failing test → bug reproduced → minimized → hypothesis
→ fixed → regression test added]

/zoom-out — High-Level Overview

When you step into a part of the codebase you don't know

Gives the agent a high-level overview of a specific directory or module, using the domain language in CONTEXT.md: which modules are dependent, who calls what, what seams exist.

claude — /zoom-out
> /zoom-out src/analytics/

Claude: The Analytics module is the service layer that
queries click records.

  LinkService → (creates a link)
  RedirectHandler → (records a click) → ClickRepository
  AnalyticsService → (reads clicks) ← ClickRepository
                   → (reads link metadata) ← LinkRepository

Callers: the GET /links/:slug/stats endpoint

/prototype — Design Decision Validation

When you're unsure about an architecture choice — to make questions like "is this strategy correct?" concrete

Validates a design decision with data using a throwaway prototype (a terminal script, minimal UI, or log analysis). It can document the result as an ADR.

claude — /prototype
> /prototype I want to test our slug collision handling
  strategy — retry, or sequential fallback?

Claude: This is a logic question — I'm building a terminal script.

[generates 10,000 slugs, measures the collision rate,
compares retry vs. sequential strategies]

Result: with 6-character alphanumeric slugs, the collision
rate at 1M slugs is 0.001%. The retry strategy is enough;
a sequential fallback is unnecessary complexity.

Should we document this result as an ADR?

Summary: The Complete Flow

The power of these skills isn't in any one of them — it's in how they work together. /grill-with-docs builds CONTEXT.md → /to-prd uses that language in the PRD → /to-issues writes issues in the same language → /tdd follows that language in tests → /improve-codebase-architecture does architectural analysis using the domain language. Result: every artifact speaks the same language and rests on the same decisions.
