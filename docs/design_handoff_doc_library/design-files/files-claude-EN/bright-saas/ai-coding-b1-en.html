Who Is This Document For?

This is aimed at software professionals who want to integrate AI coding tools into their daily workflow. The primary audience is software developers at every level, from junior to senior. The sections on clarifying requirements, producing a PRD, breaking down work, and reviewing are also directly applicable to technical leads, architects, and product managers.

This document is not tied to a specific language or tool. Examples are drawn mostly from the TypeScript/Python ecosystems, but the principles (vertical slices, TDD, deep modules, context management) are language- and tool-agnostic.

Required prerequisites

  • Basic competency in at least one language
  • Basic Git knowledge (commit, branch, merge)
  • Familiarity with any AI coding tool

Helpful but not required

  • Experience writing tests (unit, integration)
  • Command line: build, test, lint
  • Basic product development understanding
  • Knowledge of CI/CD pipelines

01

The Core Problem: AI Is Smart, But Not Unlimited

The biggest misconception with LLM-based coding agents is: "If the context window is big, I can give it everything." In practice, however, there's a dynamic you could call the Smart Zone / Dumb Zone. The model performs better at the start of a conversation; as context grows, attention relationships become more complex and the model gradually starts making worse decisions.

A model's context window might be 200K tokens — but when you load 150K tokens of code plus conversation history, the model makes far more mistakes and produces inconsistent code compared to a 20K-token session. Nominal capacity ≠ effective attention capacity.

This decline happens at different rates depending on the model and task type. The practical rule: the smaller you keep the context, the more reliably the model works. Rather than memorizing a fixed token threshold, it's healthier to actively observe response quality throughout the session and clear the context to start fresh once you feel quality dropping.

Instead of force-feeding the model a huge task, break the work into pieces small enough for the model to stay sharp.

02

Challenges Encountered During AI Coding

Click any heading to expand its description, problem, and solution.

1
Misunderstood Requirements

AI very often produces a plan far too early. You say "I want a feature like this," and the agent immediately suggests architecture, a file list, and code. But the underlying assumptions haven't been clarified yet.

Example — Gamification: When you say "add a points system," the AI produces a plan right away — but these questions go unanswered: Which actions earn points? Are already-completed lessons scored retroactively? What does the level curve look like? Where in the UI is the score shown?

Problem

AI is ready to write code, but product decisions, domain decisions, and edge-case decisions are still missing.

Solution

Alignment must happen before code. Use the AI as a "Grill Me" interrogation partner: the AI asks questions, surfaces assumptions, and builds a shared design understanding.

2
The Limits of Spec-Driven Development

A common approach: "Write a spec, let the AI turn it into code; if the code is wrong, fix the spec and regenerate." This alone isn't enough, because the developer becomes disconnected from the code. Code is still the battlefield.

Where spec-first is strong: API contract design (OpenAPI/Swagger), database migration planning, protocol/interface definitions, system integration points.

Problem

The developer gets reduced to editing specs only; code quality and architectural control are lost.

Solution

If you're writing a spec, read the code too; if you're writing code, update the spec too. The developer must understand modules, define test boundaries, and actively manage architectural quality.

3
Context Bloat and Over-Reliance on Compacting

As a session grows, the model's performance drops. Compacting summarizes history but is a limited solution. Details can be lost during summarization, and the remnants of old, no-longer-valid decisions (sediment) can mislead the agent.

Problem

In a long conversation, the agent can confuse past decisions, file changes, and intent.

Solution

Keep sessions small; clear context when needed. Write important decisions into permanent artifacts: PRDs, issues, ADRs, test plans.

4
The Tendency Toward Horizontal Implementation

AI naturally tends to split work into horizontal layers: database first, then API, then frontend. It looks classic, but feedback arrives very late. Something that actually works end-to-end only emerges in the third phase.

Vertical slice / Tracer bullet: You fire a lit round in the dark to see whether it reaches the target. A minimal schema + service + API + small UI are built together. The agent gets early feedback, and the wrong direction is caught early.

Problem

Horizontal development produces late feedback; AI writes "blind" code for long stretches.

Solution

Every issue should produce end-to-end, testable, visible value wherever possible.

5
Lack of Tests

Without a test signal, AI struggles to understand errors. It writes code, then breaks a working part while fixing another bug. TDD is an especially powerful method for AI coding: a failing test is written first, then the implementation, then the test and typecheck are run. This loop continuously signals the agent "are you on the right track?" It also reduces the agent's risk of hard-coding or taking shortcuts.

Problem

Without a feedback loop, it's unclear whether the agent is on the right track.

Solution

Unit tests, integration tests, typecheck, lint, build, and e2e tests where possible should be a mandatory part of the agent workflow.

6
Bad Architecture: Shallow Modules

John Ousterhout — "A Philosophy of Software Design" — the concepts below come from this book:

Shallow Module

A module that does very little work and exposes wide dependencies. Dozens of 10–15 line files, all importing each other. AI has to load dozens of files into context just to understand one piece of logic.

Deep Module

A module with a small, simple public interface that does meaningful work internally. Looks simple from the outside; encapsulates internal complexity. Test boundary is clear: you test the public interface.

Problem

Bad architecture lowers an AI agent's capacity for both understanding and producing tests.

Solution

Simplify module boundaries, shrink the public interface, enrich internal behavior, clarify test boundaries.

03

The Recommended AI Coding Workflow

The workflow consists of two layers:

Top layer (once)

  • If you have an idea or vision → start with Stage 0
  • If you're adding a known feature → skip to Stage 1
  • Output: a prioritized list of feature briefs

Bottom layer (per feature)

  • Each feature brief goes through Stages 1–6
  • Once a feature is done, the next brief is picked up
  • The loop starts over
0

Break the Idea into Features

product discovery Optional

When it's needed: When you don't have a clear feature brief yet — a new product idea, a major pivot, a project starting from scratch, or a broad vision.

When to skip it: If you're adding a known, well-defined feature to an existing product, skip straight to Stage 1.

In this stage, AI acts as a product discovery partner. The goal: break the idea into independent, prioritizable features that produce user value.

Decomposition Prompt

prompt
Read the idea below. Don't produce a feature list right away.

<idea>
We want to build an online education platform. Students will be
able to watch lessons, take quizzes, and earn certificates.
Instructors will be able to upload content. Gamification will
be used to boost motivation. It will be accessible on mobile
and web.
</idea>

First, interrogate me. Ask about anything unclear under these
headings:
- Who is the target user?
- What problem is being solved?
- What's the revenue model?
- What are the technical constraints?
- What's must-have for the MVP vs. what can wait?
- What are the platform constraints?

Ask one question at a time. Offer your own suggestion with
each question.

Once all questions are done, produce output in this format:
<feature_list>
## MVP Features
1. Feature name — 1-2 sentence description

## Phase 2 Features
1. Feature name — 1-2 sentence description

## Dependency Map
- Feature X → must happen before Feature Y

## Recommended Order
1. First feature (why: ...)
</feature_list>
Example output
example output
<feature_list>
## MVP Features
1. Lesson viewing — Student can watch video lessons; progress is saved.
2. Instructor content upload — Can upload video and materials.
3. Basic quiz — A multiple-choice quiz can be taken at the end of a lesson.
4. User authentication — Sign up, log in, profile management.

## Phase 2 Features
1. Gamification (points, badges, leaderboard)
2. Certificate generation and verification
3. Mobile app (native)
4. Instructor analytics dashboard

## Dependency Map
- Lesson viewing → after user authentication
- Gamification → after lesson viewing + quizzes

## Recommended Order
1. User authentication (why: foundation for everything else)
2. Instructor content upload (why: platform is empty without content)
3. Lesson viewing (why: core value for the student)
4. Basic quiz (why: validates learning)
</feature_list>

Keep the feature list in a file like docs/feature-backlog.md. Update each feature's status as it's implemented (backlog → in progress → done).

1

Interrogate the Feature Brief

analyst / product thinking partner

The first step shouldn't be "make a plan" — it should be: clarify assumptions, edge cases, the data model, test decisions, and what's out of scope, one at a time. In this stage, AI works like an analyst. The output isn't code — it's a list of clarified decisions.

Interrogation Prompt (Grill Me)

prompt
Read this feature brief. Don't produce a plan or code right away.

<feature_brief>
We're adding a gamification system to our education platform.
Students will earn points when they complete a lesson, and their
total points will show on the dashboard. Badges and a leaderboard
will be added later, but the first version is just the points
system.
</feature_brief>

First, relentlessly interview me. Question me under these
headings:
- Product goal and success criteria
- User scenarios and edge cases
- Data model decisions
- Retroactive data migration
- UI placement and behavior
- What's out of scope
- Testing decisions

Rules:
- Ask one question at a time.
- Offer your own suggestion with each question.
- Once all questions are done, summarize the decisions:

  <decisions>
  - Decision title: Description
  </decisions>
Example interrogation flow and decisions
example flow
AI: Do points only come from completing a lesson, or do actions
like taking a quiz or leaving a comment also earn points?
My suggestion: Just lesson completion for v1.

Developer: Yes, just lesson completion.

AI: There are already completed lessons in the system. Should
they be scored retroactively? My suggestion: No, only count
completions from now on.

Developer: Agreed, no retroactive scoring.

(...more questions...)

AI: All questions are done. Decisions reached:

<decisions>
- Point source: Lesson completion only.
- Point amount: 10 points per lesson completion.
- Retroactive scoring: No.
- Repeat completion of the same lesson: No points awarded.
- UI: A "Total Points" widget on the dashboard.
- Level system: Not in v1.
- Data model: points table (user_id, lesson_id, points, created_at).
- Migration: No retroactive migration.
</decisions>
2

Produce a PRD / Destination Document

build the destination document

Here, the PRD isn't a "bureaucratic document" — it's the destination document: the single reference point everyone on the team can use to answer "what are we doing, why, and where do we stand."

PRD Template — docs/templates/prd-template.md

prd-template.md
# Feature PRD: <Feature Name>

## Problem
What problem is the user experiencing?

## Goal
What outcome should this feature produce?

## Non-Goals
What's out of scope for this work.

## User Stories
- As a user, I want...

## Acceptance Criteria
- Every criterion must be testable. Don't use vague phrasing like "good experience."

## Implementation Decisions
- Reflect only the decisions from the <decisions> section — don't add new ones.

## Testing Decisions
- Unit tests, Integration tests, E2E tests, Edge case tests

## Definition of Done
- Tests pass · Typecheck passes · Build passes · Review complete

PRD Generation Prompt

prompt
Read the file docs/templates/prd-template.md.

Using the feature brief and decisions below, produce a PRD.

<feature_brief>
We're adding a gamification system to our education platform.
Students will earn points when they complete a lesson, and
their total points will show on the dashboard.
</feature_brief>

<decisions>
- Point source: Lesson completion only.
- Point amount: 10 points per lesson completion.
- Retroactive scoring: No.
- Repeat completion of the same lesson: No points awarded.
- UI: A "Total Points" widget on the dashboard.
- Data model: points table (user_id, lesson_id, points, created_at).
</decisions>

Rules:
- Fill in every section of the template.
- In Implementation Decisions, reflect only the <decisions> — nothing new.
- Every Acceptance Criteria item must be verifiable.
- Save the PRD as docs/prd/gamification-points.md.

File referencing per tool: Claude Code → read the file is enough. Cursor → @docs/templates/prd-template.md. What matters is that the template is read from a file rather than pasted into the prompt every time.

3

Split the PRD into Kanban Issues

create vertical slice issues

Instead of the classic "Phase 1: DB, Phase 2: API, Phase 3: UI," split the PRD into vertical slice issues. A vertical slice is an end-to-end slice that covers all technical layers while keeping scope narrow.

Weak issue (horizontal)

Create database schema for gamification

Can't be tested independently on its own; produces no visible result for the user.

Strong issue (vertical slice)

Award points for lesson completion and show total on dashboard

Produces end-to-end value: data + service + API + UI + test all work together.

Issue Template — docs/templates/issue-template.md

issue-template.md
# Issue <NUMBER> — <Short title>

## Type
feature | bug | refactor

## Goal
What will the user or system be able to do once this issue is done?

## Scope
- Database / schema change
- Backend service / business logic
- API endpoint
- UI component
- Test (unit, integration, smoke)

## Out of Scope
Things explicitly NOT done in this issue.

## Dependencies
Issues this depends on. "None" if there aren't any.

## Acceptance Criteria
- Criterion 1 (verifiable, no vague phrasing like "should work properly")
- Criterion 2

## Test Plan
- Unit: Which module will be tested?
- Integration: Which flow will be tested end-to-end?
- UI smoke: Which screen render will be verified?

Issue Generation Prompt

prompt
Read these two files:
- docs/prd/gamification-points.md
- docs/templates/issue-template.md

Split the PRD's scope into vertical slice issues.

Rules:
- Every issue must produce end-to-end value — no single-layer issues.
- Every issue must be independently testable and demoable.
- Number the issues in dependency order.
- Fill in the Out of Scope section explicitly.
- Save the issues as separate files:
  docs/issues/issue-01.md, docs/issues/issue-02.md, ...
- Finally, summarize the dependency graph.
Example dependency graph output
example output
docs/issues/issue-01.md → Award points for lesson completion
                          and show total on dashboard
docs/issues/issue-02.md → Prevent duplicate points for same lesson
docs/issues/issue-03.md → Admin endpoint to view user points
docs/issues/issue-04.md → Edge case handling (deleted lesson,
                          deactivated user)

Dependency graph:
- Issue 01: Independent (build first)
- Issue 02: Depends on Issue 01
- Issue 03: Depends on Issue 01
- Issue 04: Depends on Issue 01 + 02

Have the Agent Write Code with TDD

human-in-the-loop implementation

The safest implementation method in AI coding is TDD. For the agent to put tests in the right place, it needs to know the project's test conventions: defined in docs/test-conventions.md (directory structure, file naming, test format, test commands).

TDD Implementation Prompt

Used while the developer is sitting at the keyboard (human-in-the-loop), observing every step.

prompt — human-in-the-loop
Read these files:
- docs/issues/issue-01.md
- docs/test-conventions.md

Implement using the TDD loop. Read the Type field and decide your
strategy:

[If Type = feature]
  Step 1 — Write a test (Red):
  - Write at least one test per Acceptance Criterion.
  - Run the tests: npm test
  - Confirm all new tests FAIL.
    If a test passes without implementation, it was written wrong.

  Step 2 — Implement (Green):
  - Write the minimal code to pass the tests. Don't add unnecessary
    abstraction.
  - Run the tests again: npm test → all tests should PASS.

[If Type = bug]
  Step 1 — Reproduce the bug: write a failing test first. It must FAIL.
  Step 2 — Fix: minimal change. The test must PASS.

[If Type = refactor]
  Step 1 — Confirm all existing tests PASS.
  Step 2 — Refactor without changing behavior.
  Step 3 — Tests must still PASS.

[For all types]
  Step 3 — Verify:
  - npm run typecheck · npm run lint · npm run build
  - Fix any errors and re-run.

  Step 4 — Write a summary:
  ## Implementation Summary
  - Test files added: ...
  - Source files added/changed: ...
  - Test results: (paste the output)
  - Typecheck/lint/build: pass/fail
  - Out-of-scope notes: ...

What to Do When the Agent Is Stuck

If it can't solve it after 2-3 attempts, there are 4 options:

Give context, continue

For cases like a missing env variable or wrong file path, give the info and continue. No new issue needed.

Shrink the issue

Scope may be too large. Narrow the acceptance criteria, turn the rest into a new issue.

Write the hard part yourself

Write the complex part yourself (race conditions, legacy side effects). Let the agent continue with the rest.

Stop, analyze, open an issue

If it's a systemic problem, document it. Create a new issue using the Blocker Report format.

5

Human-in-the-Loop vs. AFK Task Split

task distribution and AFK execution

Not every task should be handed to AI. Some are human-in-the-loop, others can be AFK (without developer intervention).

Human-in-the-loop work
  • Requirement clarification
  • Product decisions
  • Architecture boundary decisions
  • Data model decisions
  • Risky migration decisions
  • Code review · Final QA
Work that can go AFK
  • Small issue implementation
  • Writing tests
  • Fixing typecheck / lint / build
  • Updating documentation
  • Simple refactors

Conditions and Risks of Running AFK

Safe AFK conditions
  • Issue is small and scope is clear
  • Working in a separate branch / worktree
  • Test, typecheck, and build commands are defined
  • A max-iteration limit is set
AFK risks and mitigations
  • Loop risk — set a max-10-attempts rule
  • Scope drift — fill in the Out of Scope section
  • Silent failure — include test output in the summary
  • Wrong file changes — diff review before merge

Running AFK — 3 Steps

  • 1

    Preparation (~2 min)

    Create a separate branch for the issue. Confirm the issue file and test-conventions file are ready.

    bash
    git checkout -b feature/gamification-points
# Optional: parallel worktree
git worktree add ../project-issue-01 feature/gamification-points
  • 2

    Start the Agent with the AFK Prompt

    After giving this prompt, the developer can step away from the computer.

    prompt — AFK mode
    Read these files:
- docs/issues/issue-01.md
- docs/test-conventions.md

Implement this issue.

Working rules:
1. Read the Type, Scope, and Out of Scope sections.
   Do only the work in Scope.
2. Decide your test strategy based on Type:
   - feature → Write tests first (must fail), then implement.
   - bug → Write a reproduction test first (must fail), then fix.
   - refactor → Verify existing tests, refactor, verify again.
3. Implement minimally.
4. Run the commands and confirm all pass:
   npm test · npm run typecheck · npm run lint · npm run build
5. Fix errors if any. Maximum 10 attempts. Stop if unsolved after 10.
6. Don't go outside scope.
7. When done, write an Implementation Summary.
   If unsolved, append a Blocker Report to the summary.
  • 3

    Review When You Return

    bash
    # Inspect the actual diff
git diff main...feature/gamification-points
# Check for unexpected file changes
git diff --name-only main...feature/gamification-points
# Run the tests yourself
npm test && npm run typecheck && npm run build

    After AFK coding, always review the changes by reading git diff. Trust the actual diff, not the agent's claim of "success."

Blocker Report Format

When the agent can't solve it, it appends this format to the end of the summary:

Blocker Report
## Blocker Report
### Issue
Short description: what happened?
### Error output
Relevant error message or test output
### Solutions tried
1. Attempt: ... → Result: ...
2. Attempt: ... → Result: ...
### Likely root cause
Your guess (developer should verify)
### Affected acceptance criteria
Which criterion wasn't met?
### Suggested action
- Update the scope of the existing issue
- Open a new issue (suggested title: ...)
- Environment/configuration issue — no issue needed

3 Options After a Blocker Report

A — Fix it yourself, continue

If it's a simple config or env issue, the developer fixes it and says "continue." No new issue needed.

B — Open a new issue

If the problem is outside the current issue's scope, create a new issue and feed it into the pipeline.

C — Update the existing issue

If the problem stems from a poorly defined scope, fix the existing issue instead of opening a new one.

Parallel AFK: Run Independent Issues Simultaneously

bash
git worktree add ../project-issue-01 -b feature/issue-01
git worktree add ../project-issue-02 -b feature/issue-02
git worktree add ../project-issue-03 -b feature/issue-03
# Start a separate agent session in each worktree

If there's a merge-conflict risk (issues touching the same files), run them sequentially instead. Merge order should always follow the dependency graph.

6

Improve the Codebase

avoid the shallow module anti-pattern

Work isn't done once a feature ships. If left unchecked, the speed of AI coding creates shallow module buildup: lots of small files, each dependent on another, none of them doing meaningful work on its own. Every new feature then loads more files into the agent's context and raises maintenance costs.

Signs of Shallow Modules

  • You need to open more than 5 files to understand one piece of logic.
  • Most modules are 10–30 lines, and nearly all import another module.
  • A lot is exported, but each piece does very little.
  • Testing a module requires mocking 3–4 dependencies.
  • There are "pass-through" layers: taking data and handing it to the next layer without adding anything.

Deep Module Refactoring Strategy

  1. Merge related small modules — Gather files related to the same domain concept into one module.
  2. Remove pass-through layers — Remove them if they don't provide real abstraction.
  3. Shrink the public interface — Only export what truly needs to be called from outside.
  4. Align test boundaries with module boundaries — Tests should be written against the public interface.

Refactoring with AI — 2 Steps

Step 1 — Analysis (don't change code)
Analyze this group of modules: [file list]

Answer these questions:
- Which files belong to the same domain concept?
- Are there pass-through layers?
- How wide is the public interface?
- Could we merge these modules into a deep module?

Don't change code. Present analysis and suggestions first.
Step 2 — Apply
Apply the refactoring plan you proposed.
Make sure existing tests still pass.
Add any tests missing for the new module structure.
Run test/typecheck/build after refactoring.
Note any public interface change in the summary.

When to Refactor

  • After every feature is done: Review the new files the agent added.
  • At the end of a sprint: If shallow-module buildup has increased, create refactoring issues.
  • When agent performance drops: If it's making more mistakes on similar tasks, simplify the module structure.

Keep refactoring issues small and independent, just like vertical slices. Set the Type in the issue template to refactor — when the agent sees this, it works by preserving existing tests instead of writing new ones.
