02

Folders' Responsibilities

CLAUDE.md
The main agent manifest. Project purpose, architecture rules, test commands, skill and agent workflow, agent boundaries. Long procedures go in skills/*/SKILL.md.
.claude/skills/
Reusable working disciplines. A skill is not a "role" — it is the procedure the agent applies.
.claude/agents/
Specialist agent roles. Each agent owns a specific job and may use multiple skills.
docs/CONTEXT.md
The living context file. Domain language, key concepts, system boundaries, module responsibilities, and architectural assumptions.
docs/prd/
Product requirements documents. E.g.: 001-initial-product-requirements.md
docs/issues/
Work items handed to agents. Every issue must be a vertical slice — never a horizontal layer task.
docs/adr/
Architecture Decision Records. E.g.: 0001-use-config-file-for-pricing.md
docs/architecture/
System architecture, module map, data flow, sequence diagrams, and high-level design documents.
docs/decisions/
Smaller product, technical, or process decisions that don't warrant a full ADR but still need tracking.

Put the following content in a CLAUDE.md file at your project root.

CLAUDE.md

markdown 
# Project Instructions for Claude Code

## Project Goal
This repository uses an agentic development workflow.
Claude should not work as a single monolithic coding assistant. Instead, Claude should:
1. Understand the project context.
2. Clarify requirements.
3. Produce PRDs when needed.
4. Break work into vertical slice issues.
5. Implement one issue at a time.
6. Use TDD for deterministic behavior.
7. Keep architecture decisions documented.
8. Review architecture before finalizing milestones.

## Repository Structure
Important folders:
- `docs/CONTEXT.md`: living project context and domain language
- `docs/prd/`: product requirements documents
- `docs/issues/`: agent-ready vertical slice implementation issues
- `docs/adr/`: architecture decision records
- `docs/architecture/`: high-level design and architecture notes
- `docs/decisions/`: smaller non-ADR decisions
- `.claude/skills/`: reusable workflows and engineering disciplines
- `.claude/agents/`: specialized project agents

## Default Workflow
For new features:
1. Use `/grill-with-docs` if the requirement is unclear.
2. Use `/to-prd` for medium or large features.
3. Use `/to-issues` to split PRD into vertical slice issues.
4. Use `implementation-agent` for implementation.
5. Implementation must follow `/tdd`.
6. Use `/codebase-design` when changing module boundaries.
7. Use `debugging-agent` with `/diagnosing-bugs` when tests fail unexpectedly.
8. Use `/improve-codebase-architecture` before milestone completion.

## Architecture Rules
- Prefer vertical slices over horizontal layer work.
- Keep business logic separate from presentation layers.
- Keep public interfaces small.
- Prefer deep modules over shallow modules.
- Avoid unnecessary abstraction.
- Avoid large rewrites unless explicitly requested.
- Do not duplicate business logic across UI, API, CLI, or worker layers.
- Document meaningful architecture decisions in `docs/adr/`.

## Testing Rules
- Use TDD for deterministic business logic.
- Write one failing test before implementation.
- Prefer behavior-focused tests.
- Do not couple tests to private implementation details unless necessary.
- Run relevant tests after each change.
- Run the full test suite before marking an issue complete.

## Documentation Rules
- Keep `docs/CONTEXT.md` updated when domain language or module boundaries change.
- Write PRDs under `docs/prd/`.
- Write implementation issues under `docs/issues/`.
- Write ADRs under `docs/adr/`.
- Keep README accurate for setup and usage.

## Issue Rules
Issues under `docs/issues/` must include:
- Title, User story, Acceptance criteria, Test expectations,
  Dependencies, Suggested agent, Required skills, Out of scope

Issues should be vertical slices. Avoid: "Create database layer", "Write pricing.py".
Prefer: "User can run the first CLI tracer bullet and see a cost estimate".

## Commands
```bash
# Run tests
pytest

# Run app
# TODO: add project-specific run command
```

## Safety and Scope
- Do not delete files without explicit instruction.
- Do not introduce new dependencies without explaining why.
- Do not change public behavior outside the active issue.
- Do not perform unrelated refactors.
- If a task is too broad, create or update an issue instead of coding immediately.

06

Skill Files

The following files live under .claude/skills/<skill-name>/SKILL.md. Expand for details.

skill
grill-with-docs
Clarify ambiguous requirements, establish domain language

Purpose: Clarify project intent before producing a PRD.

When to use it:

  • The requirement is broad or ambiguous
  • Project boundaries aren't clear
  • The agent is about to make an assumption
  • Shared domain language is missing
  • The user asked for a plan but key details are missing

Outputs: docs/CONTEXT.md, docs/decisions/, optional docs/adr/ drafts

Instructions:

  1. Read any existing docs: docs/CONTEXT.md, docs/prd/, docs/adr/, README.md
  2. Determine: project goal, target users, core workflows, domain vocabulary, constraints, assumptions, open questions
  3. Ask only the most important clarifying questions
  4. If there is enough context, update docs/CONTEXT.md

Rules: Don't implement code. Don't create issues (unless requested). Prefer concise context over long writing. Separate facts, assumptions, and open questions.

skill
to-prd
Convert a feature idea into a PRD

Purpose: Produce a PRD from the existing project context.

Inputs: docs/CONTEXT.md, docs/decisions/, docs/adr/, README.md, the user's request in the current conversation

Output location: docs/prd/NNN-feature-name.md

PRD structure (required fields):

  • Title, Problem statement, Goals, Non-goals
  • Target users, User stories
  • Functional requirements, Non-functional requirements
  • UX/interface expectations, Data/config requirements
  • Acceptance criteria, Out of scope, Open questions

Rules: Don't implement code. Don't produce a file-by-file implementation plan. Keep technical detail at the module-boundary level. If context is insufficient, run grill-with-docs.

skill
to-issues
Split the PRD into vertical slice issues

Inputs: docs/prd/, docs/CONTEXT.md, relevant ADRs

Output: docs/issues/NNN-short-title.md

Issue structure: Title, User story, Background, Acceptance criteria, Test expectations, Dependencies, Suggested agent, Required skills, Out of scope, Done checklist

Issues must be vertical slices. NOT "Create database layer" or "Write pricing.py" — prefer behavior-focused issues like "User can load model pricing from config and get a cost estimate".
skill
tdd
Implementation via the red-green-refactor loop

Purpose: Drive implementation through the red-green-refactor loop.

Steps:

  1. Read the issue acceptance criteria
  2. Pick a behavior
  3. Write a failing test
  4. Run the relevant test command
  5. Confirm the test fails for the expected reason
  6. Implement the smallest change that makes the test pass
  7. Run the test again
  8. Refactor once the test passes
  9. Repeat until all acceptance criteria are covered
  10. Run the full test suite before finishing

Test rules: Prefer behavior tests. Don't test private implementation details. Don't write brittle tests. Don't assert on volatile values. Use fixtures. Keep tests readable.

Implementation rules: Don't write large amounts of production code before tests. Don't add unrelated features. Don't do unrelated refactors. Stay focused on the active issue.

skill
codebase-design
Preserve module boundaries and clean design

Design principles:

  • Prefer deep modules with small public interfaces
  • Separate business logic from delivery mechanisms (UI, CLI, API, DB)
  • Keep adapters thin
  • Don't duplicate business logic
  • Avoid unnecessary abstraction
  • Use clear names from the domain language
  • Write code that both humans and agents can navigate easily

ADR triggers: Framework choice, persistence strategy, module boundary definition/change, public interface stabilization, tradeoffs future agents need to understand.

skill
diagnosing-bugs
Diagnose bugs systematically

Bug diagnosis steps:

  1. Reproduce the bug
  2. Capture the full error message
  3. Identify the smallest failing command or test
  4. Review recent changes
  5. Form a hypothesis
  6. Make the smallest change that confirms or refutes the hypothesis
  7. Re-run the failing test
  8. Only then apply the fix
  9. Run nearby tests, finish with the full suite

Rules: Don't guess and rewrite large sections. Don't fix multiple unrelated bugs at once. Don't suppress an error without understanding it. Prefer adding a regression test before the fix. Record surprising root causes in docs/decisions/.

skill
improve-codebase-architecture
Architecture review before a milestone

Review areas: Module boundaries, duplicate business logic, shallow modules, framework leakage into core logic, missing tests, confusing names, missing ADRs, inaccurate README, overengineering, under-documented decisions.

Output format:

  1. Findings — grouped by severity: critical / important / minor
  2. Suggested fixes
  3. Apply only low-risk fixes without user approval
  4. Update docs if the architecture changed
  5. Run tests after the changes

Rules: Don't do large rewrites without explicit approval. Don't change public behavior outside of bug fixes. Prefer small, reversible refactors. Preserve existing tests.

Agent Definitions

The following files live under .claude/agents/*.md. Agent = a role / specialist worker.

agent
planner-agent
Requirement clarification, PRD and issues — doesn't write code

Model: sonnet  ·  Effort: high  ·  Tools: Read, Write, Edit, Glob, Grep

Skills: grill-with-docs, to-prd, to-issues, codebase-design

Responsibilities:

  • Clarify ambiguous requirements
  • docs/CONTEXT.md updates
  • Write the PRD under docs/prd/
  • Split the PRD into vertical slice issues → docs/issues/
  • Draft ADRs under docs/adr/ for architectural decisions

Rules: Don't write production code unless requested. Don't create horizontal-layer issues. Prefer tracer-bullet issues. Every issue must include acceptance criteria and test expectations.

agent
implementation-agent
Implements a single scoped issue using TDD

Model: sonnet  ·  Effort: high  ·  Tools: Read, Write, Edit, Bash, Glob, Grep

Skills: tdd, codebase-design

Responsibilities:

  • Implement one issue at a time
  • Read the issue file before coding
  • Fully satisfy the acceptance criteria
  • Use TDD; run the relevant tests after every change
  • Update docs whenever behavior, commands, or architecture change

Rules: Don't start unrelated refactors. Don't duplicate business logic. Don't mix unrelated issues. Don't add a dependency without explaining why. Run the full test suite before finishing.

agent
debugging-agent
Diagnoses test failures and unexpected behavior

Model: sonnet  ·  Effort: high  ·  Tools: Read, Write, Edit, Bash, Glob, Grep

Skills: diagnosing-bugs, tdd, codebase-design

Responsibilities: Reproduce the bug → Find the smallest failing test → Diagnose before changing code → Add a regression test where appropriate → Apply the smallest safe fix → Run nearby + full tests

Rules: Don't rewrite large sections. Don't suppress errors without understanding the code. Don't fix unrelated issues. Record surprising findings in issue notes or docs/decisions/.

agent
architecture-review-agent
Final architecture review before a milestone

Model: sonnet  ·  Effort: high  ·  Tools: Read, Write, Edit, Bash, Glob, Grep

Skills: improve-codebase-architecture, codebase-design

Responsibilities:

  • Review architecture, module boundaries, tests, docs, and ADRs
  • Detect duplication, coupling, and overengineering
  • Apply only low-risk fixes

Rules: Don't do large rewrites without approval. Don't change public behavior outside of bug fixes. Group findings by severity. Run tests after changes.

agent
documentation-agent
Updates README, ADRs, and project documentation

Model: sonnet  ·  Effort: medium  ·  Tools: Read, Write, Edit, Glob, Grep

Skills: codebase-design

Responsibilities:

  • Keep README current; update usage commands
  • docs/CONTEXT.md updates
  • Create or polish ADRs
  • Keep docs concise and useful for future agents
  • Link related PRDs, ADRs, and issues to each other

Rules: Don't invent behavior that doesn't exist. Verify commands against the codebase where possible. Prefer concise documentation. Link related PRDs, ADRs, and issues.

10

Usage Principles

What is a skill?

A working discipline or procedure. tdd is a skill. codebase-design is a skill.

What is an agent?

A role or specialist worker. implementation-agent is an agent. It uses the tdd and codebase-design skills.

Project-level setup

Each repo keeps .claude/skills/, .claude/agents/, CLAUDE.md, and docs/. The project carries its own agentic workflow.

Personal-level setup

Use ~/.claude/skills/ and ~/.claude/agents/ to share the same definitions globally across all projects. For team projects, however, project-level is safer.

Anti-Patterns

Avoid
Build me the entire app.
Prefer
Use planner-agent to create vertical slice issues from the PRD.
Avoid
Write pricing.py.
Prefer
Implement the issue: user can load model pricing from config and get a cost estimate.
Avoid
Tests are broken, fix them.
Prefer
Use debugging-agent and diagnosing-bugs. Reproduce the failure, identify the root cause, add a regression test if needed, then fix.
